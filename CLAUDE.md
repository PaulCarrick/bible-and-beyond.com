# Bible and Beyond

A web app that answers Bible questions using AI/ML.

## Architecture
- `drupal/` — Drupal 11 (PHP), run with DDEV. Content management and admin. Exposes content via JSON:API.
- `ml-service/` — Python 3.12 + FastAPI. AI/ML logic and the question-answering API.
- `frontend/` — React + TypeScript + Vite. The public web UI; calls ml-service and Drupal.

## Local URLs
- Drupal: https://bible-and-beyond.ddev.site
- ML service: http://localhost:8000 (API docs at /docs)
- Frontend: http://localhost:5173
- Live site: https://bible-and-beyond.com (app) and https://cms.bible-and-beyond.com (Drupal); see "Production server" below

## Running locally
- Drupal: `cd drupal && ddev start` (use `ddev composer` and `ddev drush`, never local php/composer)
- ML service: `cd ml-service && source .venv/bin/activate && uvicorn main:app --reload --port 8000`
- Frontend: `cd frontend && npm run dev`
- If something else already uses port 8000 (Docker sometimes does), run uvicorn on 8001 and put `VITE_ML_SERVICE_URL=http://localhost:8001` in `frontend/.env.local` (git-ignored).

## Conventions
- No abbreviations in variable, function, or method names.
- 2-space indentation in PHP, TypeScript, JSON, YAML; follow the formatter's default for Python.
- Keep solutions simple and direct; avoid unnecessary abstractions.
- Show complete files/functions when making changes.
- Never commit secrets; use `.env` files (gitignored) and keep a `.env.example`.

## Testing
- Python: pytest — `cd ml-service && source .venv/bin/activate && python -m pytest`
- Frontend: Vitest (to be added)
- Drupal: PHPUnit via `ddev exec vendor/bin/phpunit` (to be added)

## Bible database
- Postgres 17 + pgvector in Docker (`docker compose up -d` from the repo root), container `bible-and-beyond-database`, host port 5434.
- Connection string lives in `ml-service/.env` as `DATABASE_URL` (never commit `.env`).
- Schema: `ml-service/database/schema.sql` — tables `translations`, `books` (canonical 1–66 with USFM codes and name aliases), `verses`, `verse_embeddings`. Applying it drops and recreates these tables.
- Import a translation (BSB tab format or eBible `*_vpl.txt` format): `.venv/bin/python scripts/import_bible.py data/<file>.txt --code BSB --name "Berean Standard Bible" --license "Public domain"`. KJV also needs `--strip-brackets`.
- Search in public-domain text (BSB); copyrighted translations like ESV are only fetched for display, never stored.
- Each translation has an `is_published` flag. Search and the Bible picker only see published ones. Database changes live in `ml-service/database/migrations/` as files that are safe to run twice; `deploy/deploy.sh` applies them. `schema.sql` is kept in step for fresh databases.
- The importer lives in `ml-service/bible_import/`; `scripts/import_bible.py` (command line, publishes at once unless `--unpublished`) and `scripts/manage_bibles.py` (JSON output, used by Drupal) both call it.

## Licensed Bibles (API.Bible)
- NIV, NASB 2020 and The Message come from API.Bible (free Starter plan: non-commercial only, 5,000 requests a month). Code is in `ml-service/api_bible.py`; the key and endpoint are `API_BIBLE_KEY` and `API_BIBLE_ENDPOINT` in `ml-service/.env`.
- Their text is never stored in our database; it is fetched on demand and cached in memory (search results 10 minutes, copyright metadata 24 hours; the terms require refreshing within 30 days).
- Terms to keep: show each Bible's copyright notice with its text, keep the API.Bible link and the "Bible copyright notices" page (now on the Help page and under licensed search results, no longer in the footer), and report every view to FUMS (`frontend/src/fums.ts`). Never alter the text, never use it commercially, and never put it in AI prompts or training data. Use only the public-domain local Bibles (ASV, BSB, KJV, WEB) for `/ask`.
- These Bibles are searched one at a time, matching all words, in Bible order. Match any, exact phrase, whole words, per-book counts and sorting by contents are not available for them.
- Backend tests fake the API so they do not use the monthly allowance. Live calls count against it, so keep them few.

## Managing Bibles from Drupal
- Drupal is the admin screen for the main site; the Bible text goes into the main PostgreSQL database, never into Drupal's. Page: https://cms.bible-and-beyond.com/admin/bibles (Drupal module `drupal/web/modules/custom/bible_admin`).
- Flow: upload a `.txt` file with a code, name, language and license; see a preview (format, verse and book counts, sample verses, warnings); confirm to import. A new Bible is **hidden until published** (Publish / Hide / Delete on the list page). Re-importing an existing code replaces its text and keeps its published state. The last published Bible cannot be hidden or deleted. The codes NIV, NASB and MSG are refused (they belong to API.Bible).
- Drupal runs `ml-service/scripts/manage_bibles.py` with a fixed argument list (no shell). The uploaded file is kept in `/home/paul/drupal-private/bible-uploads/` only until the import is confirmed or cancelled, and stale ones are removed by cron after a day. Check the Drupal log (type `bible_admin`) to see who imported, published or deleted what.
- Roles: `administrator` (everything, including adding users) and `Bible administrator` (the Bibles page and, on the Site settings screen, only the verse-window numbers). Add people at People > Add user. The server cannot send email, so set each new user's first password yourself and tell them privately.
- Adding a file format (USFM, XML, ...): write a reader class in `ml-service/bible_import/formats.py` (same members as `TabSeparatedReader`: `id`, `name`, `description`, `score`, `read`) and add it to `READERS`. Detection, the preview, the import and the Drupal format list pick it up automatically. Add tests in `ml-service/tests/test_bible_import.py`.
- The Drupal module has no automated tests yet (PHPUnit is not set up); the Python side does.

## FAQ (answers from Google Gemini)
- "FAQ" in the sidebar (group About; `FaqPage.tsx`, also mentioned under the welcome cards and on the Help page): a select list of 30 fixed questions in six groups (`<optgroup>`), a "Show the answer" button, a waiting line, then the answer and a note that it was written by an AI and may contain mistakes. The page stays mounted and keeps the answers it has shown.
- Backend `ml-service/faq.py`: the questions (`QUESTION_GROUPS`, numbered 1 to 30 in order), the system prompt (historic, Bible-centred Christianity; cite references rather than quote; describe the main views fairly where Christians differ; gentle on painful subjects; simple Markdown), and the call through the `google-genai` SDK. `GET /faq` returns the groups and `available` (whether a key is set); `POST /faq/answer` takes `{question_id}` only, never free text, so nothing else can be asked (unknown number 404; no key or a Gemini failure 503 with a general message; the cause is logged).
- **Key**: `GEMINI_API_KEY` in `ml-service/.env` (never committed; https://aistudio.google.com/apikey); `GEMINI_MODEL` is optional: the models to try in order, separated by commas (default `gemini-3.6-flash,gemini-flash-latest`). Google's models are sometimes too busy (503 "high demand" or 504), so when one fails the next is tried, 40 seconds each. Checked on 2026-11-07: 3.6 answered in 13 to 15 s; 3.7 and 3.8 timed out, `gemini-flash-latest` was overloaded, and 2.5 is retired for new keys. Without a key the page lists the questions and says the answers are not available.
- **No Bible text goes into the prompt**, only the question; the prompt tells Gemini to quote only public-domain translations (KJV, ASV, WEB, BSB) and never the NIV, NASB or The Message.
- **Caching**: each answer is kept in memory for 24 hours (`ANSWER_CACHE_SECONDS`), one lock per question so visitors asking at once cause one call; failures are not kept. So at most about 30 Gemini calls a day, plus one per question after each restart of the ML service.
- nginx limits `/api/faq/answer` to 10 a minute per visitor (burst 5, zone `api_faq`, 90 s read timeout; install with `install-system-config.sh`). The answer is drawn by `MarkdownText.tsx` (paragraphs, `##` headings, lists, bold and italic as React elements; anything else, HTML included, shows as plain text). Tests fake Gemini and the verse table (`tests/test_faq.py`, 14).
- To go live: put `GEMINI_API_KEY` in the server's `ml-service/.env`, install the nginx change, deploy, then read a few answers (especially the contested questions) before telling people about the page. Not built: answers written ahead of time and reviewed by a person.
- **Links**: the Scripture references in an answer are links that open the Bible reader (BSB) at the verse a reference begins at. The server finds them with `find_references` (`scripture_references.py`, the commentary reference finder, so a verse that does not exist stays plain) each time an answer is sent, cached or not, and returns `references` (`{text, book, chapter, verse}`, each text once); the page links every occurrence of those exact words, in bold and italic too (`links` on `MarkdownText.tsx`, longest first so "1 John 4:7" is not taken for "John 4:7"). If the verse table cannot be read the answer shows without links. The AI note under each answer quotes 1 John 4:1 (BSB) with a link to it.

## Contact form (main site)
- "Contact" in the sidebar (group About; `ContactPage.tsx`, also linked from the welcome page): full name, email, optional phone, and a message written in **Quill** (npm `quill`, snow theme; toolbar of bold, italic, strike, link, heading, quote, code, lists, undo and redo; no attachments), and Google **reCAPTCHA v3** (no box: the page gets a token when Send is pressed; the badge is shown and the page names Google's policies). The page stays mounted so a half-written message is not lost.
- Keys go in `ml-service/.env` (never committed): `RECAPTCHA_SITE_KEY` (public; the page fetches it from `GET /contact-settings`, and the form says it is unavailable when it is empty) and `RECAPTCHA_SECRET_KEY`. Create a **v3** key pair at https://www.google.com/recaptcha/admin with the domains `bible-and-beyond.com` (and `localhost` to try it locally). A v2 key gives "Invalid key type". The server accepts a score of `RECAPTCHA_MINIMUM_SCORE` or more (0.5 when not set) for the action `contact`; a refusal is logged with its score so the limit can be tuned.
- `POST /contact` (`ml-service/contact.py`): checks the fields (one line each, valid email, up to 5,000 characters of message), then the reCAPTCHA token with Google (success, action and score), then cleans the message HTML (an allowlist: paragraphs, bold, italic, strike, links with http(s) or mailto only, quotes, code, lists, headings; scripts, images and event attributes are dropped) and sends a plain-text and an HTML email. A bad message is refused before Google is asked.
- **Where the email settings come from.** They are the ones on the Drupal Site settings screen (host, port, user, password, authentication, From, To, subject). The password is only in Drupal, so for each message the ML service runs `drush php:eval` (`drupal/vendor/bin/drush`, or `DRUSH_COMMAND` in `.env`, e.g. `ddev drush` on a Mac) to read `MailSettings::load`, uses them for that one message and logs nothing from them. Mail goes out with Python's `smtplib` (STARTTLS on 587, SSL on 465, the chosen sign-in method). The visitor's address is the Reply-To; From is the site's address. A failure is logged and the visitor sees only a general "could not be sent" message (502).
- nginx limits `/api/contact` to 3 a minute per visitor (burst 3; `deploy/nginx/`; install with `install-system-config.sh`). The tests fake Google, drush and the mail server (`tests/test_contact.py`); a real send was checked locally against a stand-in mail server.
- To go live: put the two keys in the server's `ml-service/.env`, type the email password on the Site settings screen, install the nginx change, then deploy. The subject still says "Contact request from Paul-Carrick.com." until changed there.

## Accounts (main site visitors, not Drupal)
- Optional: nothing requires logging in; accounts are for user-specific features to come. The header has "Set up account" and "Log in" links (and, when logged in, the address and "Log out"; `SiteHeader.tsx`, `AccountPage.tsx`, pages `register` and `login` in `views.ts`). Set up account asks for an email and the password twice (at least 10 characters, at most 128, no other rules) and logs the visitor in; Log in asks for email and password. `App.tsx` asks `GET /account/me` on load.
- Backend `ml-service/accounts.py`, endpoints `POST /account/register`, `/account/login`, `/account/logout`, `GET /account/me` in `main.py`. Tables `users` and `user_sessions` (migration 010). **They are not in `schema.sql` on purpose**: applying `schema.sql` drops and recreates the Bible tables, and it must never wipe accounts. They are in the Bible database, so backups include them (and a restore of an older backup loses newer accounts).
- Passwords: salted **scrypt** (N=2^15, r=8, p=1; Python's `hashlib`, no extra package), stored as `scrypt$N$r$p$salt$hash`, never logged or returned. A wrong password and an unknown address give the same 401 message and take about the same time. Email addresses are stored in lower case and are unique.
- Sessions: a random token in the cookie `session` (HttpOnly, SameSite=Lax, Secure over HTTPS, 30 days); the database keeps only its SHA-256, so a copy of it cannot log anyone in. Logging out deletes the session; expired ones are removed at each login. CORS allows credentials for `ALLOWED_ORIGINS` (explicit origins only; the page uses `credentials: 'include'` for the account calls).
- nginx limits `/api/account/register`, `login`, `verify`, `resend-verification`, `forgot-password` and `reset-password` to 10 a minute per visitor (burst 5). Install with `install-system-config.sh`.
- **Email verification and password reset** (migration 011: `users.email_verified_at`, table `account_tokens`). Setting up an account emails a link (`/?verify=TOKEN`, good for 72 hours, once); the account works before it is followed (the page shows a reminder with "Send it again"), and features that need a confirmed address can check `email_verified` from `GET /account/me`. "Forgot your password?" on the Log in page asks for an address; `POST /account/forgot-password` always gives the same answer and sends after answering (as a background task), so neither the words nor the time reveal whether an address has an account. The reset link (`/?reset=TOKEN`, 60 minutes, once) lets the visitor choose a new password; that logs every session of the account out and counts as confirming the address. A bad new password does not use the link up. Links are random, stored only as SHA-256, replace any earlier link of the same kind, and a new one is not sent to the same account within 60 seconds. The page takes the token out of the address bar at once, and calls the server once per link (`VerifyEmailPage.tsx`; React runs effects twice in development, which used up a link the first time it was tried).
- The emails go out through the same path as the contact form (`send_plain_message` in `contact.py`: Drupal's email settings via drush, then smtplib), from the site's "Email From:" address, so **the email password must be set on the Site settings screen**. `SITE_URL` in `ml-service/.env` is the address put in the links (`https://bible-and-beyond.com` when not set; use `http://localhost:5173` locally). A failure to send is logged without the link and never stops sign-up; the visitor can ask again. Locally, test with a stand-in mail server and `DRUSH_COMMAND` pointing at a script that prints the settings JSON.
- Not built (on purpose, for later): changing the password or the address while logged in, deleting an account, a list of common passwords to refuse, and any feature that uses the account. Tests: `tests/test_accounts.py` (24; they collect the emails instead of sending).

## Notes (logged-in visitors)
- A user has many notes (`notes` table, migration 012, `ON DELETE CASCADE` from `users`; like `users` it is not in `schema.sql`, so re-applying that file cannot wipe it). A note has `created_at` and `updated_at`, an `item_type` (`bible_verse`, `commentary` or `devotional`), where it is, and a `body` of cleaned HTML from the editor. Where it is: `source_code` (the translation read, or the commentary id, or the devotional id) and, for a verse or a commentary note, `book_number`, `chapter`, `verse` (numbered like the KJV, as everywhere here); for a devotional, `section` and `unit` as the devotional reader numbers them. A table `CHECK` keeps the fields that belong to each type and nothing else.
- API (`ml-service/notes.py`, endpoints in `main.py`; all need the session cookie, else 401): `POST /notes`, `GET /notes`, `PUT /notes/{id}` (replaces the text, sets `updated_at`; the item never changes) and `DELETE /notes/{id}`. Only the owner can change or delete a note (anyone else gets 404). Each note in an answer has a `title` saying what it is about ("John 3:16", "Genesis 1:1–2 (Matthew Henry)", "November 4 (Morning and Evening)"; built in `_describe`). A note on a verse must name a verse that exists in some Bible here. One account can keep 5,000 notes (`MAX_NOTES_PER_USER`). `GET /notes` returns `{notes, total, page, per_page}`: `page` (from 1) and `per_page` (1 to 200, default 200, which is what the notes windows use), `item_type` alone to keep one kind, the place as well for one item, and `query` to keep the notes whose text has every word (up to 10), in any case and any part of a word (`ILIKE` on `body_text`, with `%` and `_` taken literally). Migration 013 added `body_text`, the note's plain text (tags are not searched, and it is set from the cleaned note on every save; the migration fills it for older notes). The title ("John 3:16", the commentary or devotional name) is not searched, only what the visitor wrote. The list calls: (the visitor's own notes, newest first, up to 200; with `item_type` and the place only the notes about that item). A verse is the same item in every Bible, so a note written in the KJV shows when the BSB is read; a commentary note also matches its commentary. The body is cleaned with the same allowlist as the contact form (`check_rich_text` in `contact.py`): at most 10,000 characters of text. Tests: `tests/test_notes.py`.
- The **"Notes" link** opens a window (`ContextKind` `note`, `NotesPanel.tsx`) with the editor (`RichTextEditor.tsx`, the Quill editor shared with the contact form) and Save, and below it the visitor's earlier notes on that item with the date and time. Logged out, the window says notes need an account and offers Log in and Set up an account (`AccountContext.ts` tells the windows who is logged in). A window says what it is about with `VerseTarget.subject` (`NoteSubject` in `types.ts`); without one it is a verse. The links:
  - **Bible verse**: the last link of a search result (local Bibles), the last item of the reader's verse menu, and the **verse numbers in the Show in Context and Full Chapter windows** (each number is a button with the label "Notes on John 3:16", in the tab order; a hint line says so; the notes window opens on top and Back returns to the passage).
  - **Never put a `<form>` inside a window.** The windows open inside the search pages, which are themselves a form (`SearchForm.tsx`); a Save button in a nested form submits the search instead, reloads the page and saves nothing. This broke saving a note from a search result for a while (the notes window used a form; found on 2026-11-07 and fixed). `NotesPanel.tsx` and `NoteCard.tsx` use a plain container and a `type="button"` Save.
  - **Commentary note**: "Notes" on each note in Browse the commentaries (`BrowseTab.tsx`), on each commentary search result, and under "notes on ..." in the Commentaries window (`CommentaryPanel.tsx`, opens on top of the window, Back returns). A commentary note is identified by its commentary and the verse it **begins** at (`start_verse` on each commentary in `GET /commentaries`, and `note_verse` for the one shown), so the same note reached from any of the three links shows the same notes. Notes on different commentaries of the same verse are separate.
  - **Devotional reading**: "Notes" under the heading of each day or chapter in the devotionals reader (`DevotionalsTab.tsx`), kept by devotional, section and unit; a daily reading's morning and evening share one note list. The window's `VerseTarget` carries zeros for the verse (a reading has none).
- **My notes** (`NotesPage.tsx`, the "My notes" link in the header beside the email when logged in; `NoteCard.tsx` is one note with Edit, Delete and an inline "Yes, delete it" confirmation, also used in the notes windows): every note newest first with its title, date and time (and "edited" with the change time), a filter by type, and "Add a note" for a **Bible verse**. The page runs from the filter and search, through the count and the list and its paging, to the add form at the bottom; the "Add a note" button beside the filter opens the form and scrolls to it (a book, chapter and verse and the editor; notes on a commentary note or a devotional reading are added from the Notes link beside them, because choosing those from a form would need pickers). It is paged 25 at a time (First, Previous, Page x of y, Next, Last) with a search box (Search, Clear search) and the kind filter, all done by the server; each note has a link to its item ("Open in the Bible", "Open the commentary note", "Open the reading"): `App.tsx` `openNoteItem` sets a `Destination` (`types.ts`, with a new id each time so the same link works twice) and shows that reader, and `BibleTab`, `BrowseTab` and `DevotionalsTab` take it as a `destination` prop and `go` there (an effect placed before their start effect, which it also stops from starting the tab twice). A verse opens in the Bible the note was written in when it can be read here, else the BSB; a commentary or devotional that no longer exists falls back to the first. The link is only on the My notes page, not in the notes windows, which are already about the item. A count line says how many notes there are or match, and deleting the last note of the last page shows the page before. After adding a note the list returns to page 1 with no search or filter, so the new note shows.
- **Search words are highlighted** in the notes on the My notes page: `highlightHtml.ts` parses the note's (server-cleaned) HTML and wraps matches in `<mark>` in its text nodes only, so a link's address or a tag is never touched; same matching as the server (any case, any part of a word, special characters literal). Only the search that is showing is highlighted (not what is being typed), the title is not, and the editor always holds the note as written. The notes windows have no search, so no highlighting there.
- Not built yet: searching by title, sorting oldest first, and anything that uses the notes (search, export). The contact page loads Google's reCAPTCHA script only when it is opened.

## Daily devotional emails
- A logged-in visitor with a **confirmed email address** can have a devotional emailed every day. On the devotionals page, under the choosers, "Email me this devotional each day" (`DevotionalEmailPanel.tsx`, a `<details>`): a time of day and a time zone (the browser's by default; `Intl.supportedValuesOf`), and for a devotional with chapters the chapter to start with (the one on screen by default). Once subscribed it says when, and offers "Change the time" and "Stop the emails". It applies to that devotional only; one subscription per devotional per user.
- What is sent: a **daily** devotional (Morning and Evening, Daily Light) sends the reading for the visitor's **own local date** (the morning and evening readings together; February 29 works); one with **chapters** (the Imitation, the Practice) sends one chapter a day in order from the starting chapter and stops, with a closing line, after the last. Plain text, from the "Email From:" address on the Site settings screen, sent with Drupal's email settings through the same path as the contact form (`load_mail_settings`, once per run). Subscribing after the day's time has gone by starts tomorrow (nothing is sent at once).
- Tables: `devotional_subscriptions` (migration 014): `send_time` and `timezone` (IANA name), `next_section`/`next_unit` for chapter devotionals, `last_sent_on` (the visitor's local date), a failure counter, and `unsubscribe_token`. There is **no foreign key to `devotionals`**, so reloading a devotional never removes subscribers; deleting a user removes theirs. Not in `schema.sql`, like the other account tables.
- **The sender** is `ml-service/subscriptions.py` `send_due`, run by `scripts/send_devotional_emails.py`, which a **systemd user timer** starts every 5 minutes (`deploy/systemd/bible-and-beyond-devotional-emails.{service,timer}`; `deploy.sh` installs both and runs `systemctl --user enable --now` on the timer when `deploy/systemd/` changes; `Persistent=true`; the user lingers, so it runs without a login). So an email arrives within about five minutes after the chosen time. It is the only scheduled job on the server (backups stay manual). Check it with `systemctl --user list-timers` and `journalctl --user -u bible-and-beyond-devotional-emails`.
- Safety of the sender: only one run sends at a time (Postgres advisory lock 7281001); a subscription claims today's date **before** sending, so nothing can be sent twice; a failed send is put back and tried at the next run, up to 3 times a day, and a chapter devotional does not move on after a failure; at most 50 emails per run (`EMAILS_PER_RUN`, the rest wait for the next run) with a one-second pause (the mail server has its own limits: the paul-carrick.com one is whatever the host allows, so watch it if many people subscribe); addresses that are not confirmed are never sent to.
- **Unsubscribing**: every email ends with a link (`/?unsubscribe=TOKEN`, `UnsubscribePage.tsx`) and carries the one-click headers `List-Unsubscribe` and `List-Unsubscribe-Post` (RFC 8058) pointing at `POST /api/subscriptions/unsubscribe?token=`; no login needed, and the token can do nothing but stop that one subscription. `SITE_URL` (in `.env`) is the address put in the links.
- API (login needed except the last): `GET /devotional-subscriptions`, `PUT /devotional-subscriptions/{devotional_id}` (`send_time` "HH:MM", `timezone`, optional `start_section`/`start_unit`; 403 until the address is confirmed), `DELETE /devotional-subscriptions/{devotional_id}`, `POST /subscriptions/unsubscribe?token=`. nginx limits the unsubscribe endpoint (10 a minute, same zone as login). Tests: `tests/test_subscriptions.py` (20; they fake the mail server and pass the time in). A real run was checked locally with a stand-in mail server: nothing at the first run, one email on a new day, nothing again.
- Not built: a page listing all of a visitor's email subscriptions (each is managed on its devotional's page, or from the email), other delivery methods (the table is per devotional, not per method), HTML emails, the "Read online" deep link into a day, Bible verse or commentary emails, and a daily cap on how many people can subscribe.

## Search results layout
- The results of a search (Bibles or commentaries) take the whole width of the page. There is **no sidebar**: the **Filters** (keep the results to one book, each book with its count; `ResultFilters.tsx`, built by `SearchTab.tsx` and passed to `SearchForm.tsx` as the `filters` prop) and the **"Results per page"** choice are both in the **Search Options** box under the results (the per-page choice used to be in both places). The count line is just "583 Bible results" (or "459 commentary results"), at the **far right of the Verse / Contents row** of the list (`.results-summary`); it is the heading above the list only where that row is not shown (a phone, while searching, or with no results). The query and the Bibles searched are not repeated in it (the owner asked for it short). When a book is chosen it adds "· only Genesis" and a "Show all books" link, so that is visible with the options closed. The licensed Bibles show no filters (their results cannot be counted by book). The filter list is a box of its own that scrolls (`.filters`, 18 rem).

## Show in Context
- **Layout of the links** (`App.css`: `.result`, `.verse-column`, `.verse-links`, `.context-link`): the links of a result (seven now) are on a line of their own under the reference and the verse text, across the whole result and flush left, in 12.5 px type with thin lines between them, so they fit on one line at normal widths and wrap neatly on a phone. `.verse-column` is `display: contents`, so the result row itself places the text beside the reference and the links on a full line below. The line before the first link of a row is hidden by pulling the row left and clipping it (each link also has `margin-left: -1px`); keep that if the links are restyled.
- Each verse in a result from a Bible stored on this site has four links, "Show in Context", "Full Chapter", "Other Translations" and "Related Verses". Each replaces the result list with a window and an X (or Escape) that goes back to the same results. The first two highlight the chosen verse (search words in bold only there). Show in Context shows some verses before and after it in reading order, with chapter headings when it crosses a chapter. Full Chapter shows the whole chapter that contains the verse and ignores the numbers below. Other Translations lists the same verse in every published Bible stored on this site (the one searched comes first, marked "This result"); a Bible that lacks that verse is left out. Results from the licensed Bibles (NIV, NASB, The Message) have no link: it would cost API.Bible requests and the text would have to be split into verses.
- The window stops at the start and end of the book. How many verses come before and after is set in Drupal at https://cms.bible-and-beyond.com/admin/site-settings (the Site settings screen) (defaults 5 before and 10 after, each 0 to 50), together with how many related verses to list (default 10, 1 to 50). They live in the `site_settings` table (migration 002), so changes apply to the public site at once. Same permission as the Bibles page.
- Code: `GET /context`, `GET /chapter`, `GET /parallel` and `GET /related` in `ml-service/main.py` and `ml-service/context.py`; settings in `ml-service/site_settings.py` and `scripts/manage_settings.py` (JSON, used by Drupal); frontend `ContextWindow.tsx` and `SearchResults.tsx`.

## Related Verses (cross references)
- Data: OpenBible.info's cross references (https://www.openbible.info/labs/cross-references/), **licensed CC BY 4.0**, based mainly on the Treasury of Scripture Knowledge (public domain). The license requires credit, which the Related Verses window and the "Bible copyright notices" page give (`frontend/src/CrossReferenceCredit.tsx`). It says the data was reformatted and that links with no positive votes were left out; keep that true if the import changes.
- It lives in the `cross_references` table (migration 003; about 341,000 rows, 42 MB), numbered like the KJV and not tied to one translation. A reference points at a verse or a range. Votes are OpenBible.info users' ranking of how useful a link is; rows with zero or negative votes are not loaded.
- Load or refresh it by hand (the deploy script only warns when the table is empty): download `cross-references.zip` from the page above, unzip it, then run `ml-service/.venv/bin/python ml-service/scripts/import_cross_references.py cross_references.txt` (`--dry-run` first). It replaces every row in one transaction. Its first line carries the release date; the one loaded on 2026-11-06 was dated 2026-11-02.
- `GET /related?translation=&book=&chapter=&verse=` lists the best-voted references first, with their text in the Bible searched, a range expanded to at most 15 verses, and a reference to a verse that Bible lacks shown without text. Only Bibles stored on this site get the link; the licensed Bibles do not.
- The window has two tabs: "Points to" (where the verse points) and "Pointed to by" (`direction=to`: the verses that have a reference beginning at it, or a range inside its chapter that contains it; a range that starts in an earlier chapter and runs through it is not matched). The data is one-way, only 25% of pairs also appear in reverse, so "Pointed to by" is a real second list (John 3:16 points to 23 verses and is pointed to by 104). Migration 004 adds the index for it.
- Each related verse has its own "Show in Context" and "Related Verses" links. They open another window on top, so you can follow a chain of references; Back goes up one level and the X or Escape closes them all and returns to the results (`WindowView` stack in `SearchResults.tsx`, `RelatedPanel.tsx`).

## Original Words (Hebrew and Greek, Strong's lexicon)
- Data: STEPBible-Data (https://github.com/STEPBible/STEPBible-Data) from STEP Bible and Tyndale House, Cambridge, **licensed CC BY 4.0**. Its README and file headers allow including the data in software without asking permission and require credit to "STEP Bible" with a link; they ask people not to post copies of the data files elsewhere. So: the files are never committed (the repository is public; `ml-service/data/stepbible/` is git-ignored), the site offers no download of them, and the API only returns the entries for one verse or one word at a time. Credit is in `frontend/src/StepBibleCredit.tsx`, shown in the Original Words and lexicon windows and on the "Bible copyright notices" page. It says the data was reformatted and that only the Greek words of the modern critical text (NA27/28) are loaded; keep that true if the import changes.
- Tables (migration 005): `original_words` (about 441,000 rows: book, chapter, verse, position, original text, transliteration, English, Strong's number, grammar) and `lexicon_entries` (about 22,700 rows). Verses are numbered like the KJV (TAHOT gives that first, with the Hebrew numbering in brackets), not tied to one translation.
- Load or refresh it by hand (the deploy script only warns when `original_words` is empty): download these into one folder, for example `ml-service/data/stepbible/`: the four TAHOT files and the two TAGNT files from "Translators Amalgamated OT+NT", and TBESH and TBESG from "Lexicons" (names may be shortened but must start with tahot, tagnt, tbesh or tbesg). Then run `ml-service/.venv/bin/python ml-service/scripts/import_original_words.py <folder>` (`--dry-run` first). It replaces every row in one transaction. Loaded on 2026-11-06 from the files on GitHub that day (441,490 words, 22,717 lexicon entries).
- Hebrew words come from the Leningrad reading only (type `L`); a joined word such as `H9003/{H7225G}` keeps the number in braces. Greek words are those whose type starts with N (NA27/28); words found only in the Textus Receptus (such as John 7:53 to 8:11) have none. A few tags carry a sense letter the lexicon lacks (H0430J, G2453); they fall back to the "G" entry of the same number (`resolve_strong_code`).
- `GET /original-words?book=&chapter=&verse=` (the words of a verse, each with its lexicon gloss, 404 when none) and `GET /lexicon?translation=&strong_code=` (an entry, the number of verses that use the word, and the first 30 in Bible order with their text in the Bible searched; licensed Bibles get 422). Code: `ml-service/original_words.py`; frontend `WordsPanel.tsx`, `LexiconPanel.tsx`, and the "Original Words" link in `SearchResults.tsx`. Each lexicon verse has "Show in Context" and "Original Words" links, so the windows chain like Related Verses. Only Bibles stored on this site get the link.
- Search by Strong's number: a search box query that is only a number (`G25`, `g0025`, `H7225`, `H7225G`; letters and spaces forgiven, parsed by `parse_strong_query` in `ml-service/search.py`) lists the verses that contain that Hebrew or Greek word, in the Bibles chosen, with the usual book filter, sorting and paging (the match options do not apply and nothing is bolded). A number without a sense letter also matches its senses (H7225 covers H7225G and the others); a letter narrows it (H7225G only). The response adds `strong` (the lexicon entry chosen: the number itself, else its "G" sense, else the first) and the page shows a note under the heading with an "Open the lexicon entry" link (`openLexicon` in `SearchResults.tsx`; it opens the same lexicon window as a Strong's number in Original Words, with the first Bible searched for the verse text). A number that is not in the lexicon gives a 422 message; the licensed Bibles refuse it (422). A real English search that happens to look like a number (for example "H1") is treated as a Strong's search.
- Click an English word (Berean Standard Bible only): in the Show in Context and Full Chapter windows, the words of a BSB verse are buttons that open the lexicon entry of the Hebrew or Greek word behind them (a hint line says so; Back returns to the passage). Data: the Berean Bible's translation tables, `bsb_tables.tsv` (https://bereanbible.com/bsb_tables.tsv, about 85 MB), **public domain** (the Berean texts were placed in the public domain on 2023-04-30), so no credit is required. The file is git-ignored (`ml-service/data/bsb_tables.tsv`). It lists every original word with its Strong's number and the BSB English for it, in English order. We do not rebuild verses from it (spacing and punctuation differ); `ml-service/word_links.py` walks its English words in order and matches them to the words of our stored text, and a verse gets links only if every table word is found in order (on 2026-11-06: 31,082 of 31,086 verses, 719,917 linked words). Links are stored in `verse_word_links` (migration 006) as `[start, end, "H7225"]` over the verse text, with the md5 of the text they were made for; the lookup ignores them if the verse text has changed, so **run the loader again after re-importing the BSB**: `ml-service/.venv/bin/python ml-service/scripts/import_word_links.py ml-service/data/bsb_tables.tsv` (`--dry-run` first; the deploy script warns when the table is empty). The numbers are plain Strong's numbers ("H7225"); `/lexicon` accepts them and gives the main entry with the verses of every sense. Common words such as "the" and "and" are linked too, to what the table says they translate. The buttons are out of the tab order (hundreds per chapter); keyboard users use the Original Words window, which lists the same numbers. Not done: other Bibles (a public-domain Bible with Strong's numbers, such as the KJV, would need its own data), and the result rows themselves (only the two reading windows have clickable words).

## Commentaries (public domain)
- Six commentaries, each marked **Public Domain** (https://creativecommons.org/publicdomain/mark/1.0/) by the Free Use Bible API (https://bible.helloao.org, AO Lab; its code is MIT, and it serves one JSON file per chapter at `/api/c/<id>/<BOOK>/<chapter>.json`): Matthew Henry, John Gill, Adam Clarke, Jamieson-Fausset-Brown, John Calvin, and Keil and Delitzsch (Old Testament only). Its seventh, the Tyndale Open Study Notes, is CC BY-SA, not public domain, and is not used. The credit is a courtesy (`frontend/src/CommentaryCredit.tsx`: in the window and on the "Bible copyright notices" page). The texts are the old editions as converted by that project, so spelling, wording and the odd conversion flaw are theirs.
- Tables (migrations 007 and 008): `commentaries` (id, names, order), `commentary_entries` (book, chapter, verse, end_verse, text; about 78,000 rows, 134 MB) and `commentary_introductions` (book introductions are chapter 0). Verses are numbered like the KJV. An entry covers `verse` to `end_verse`; NULL means to the end of its chapter. Gill, Clarke and Jamieson-Fausset-Brown comment verse by verse and skip some verses; Henry, Calvin and Keil and Delitzsch comment on sections, so an entry runs from its verse to the next entry (`COMMENTARIES` in `ml-service/commentaries.py` says which is which).
- Download and load by hand (the deploy script only warns when `commentary_entries` is empty). The files are git-ignored (`ml-service/data/commentaries/`, about 245 MB): `ml-service/.venv/bin/python ml-service/scripts/download_commentaries.py ml-service/data/commentaries` (about 6,000 files, a few minutes, four connections at a time, can be stopped and rerun; a few chapters do not exist on the host and are skipped), then `ml-service/.venv/bin/python ml-service/scripts/import_commentaries.py ml-service/data/commentaries` (`--dry-run` first; replaces each commentary in one transaction; name commentaries after the folder to load only some). Downloaded and loaded on 2026-11-06: 78,000 entries. To put the files on the server, send a compressed tar of the folder with `scp` (not committed).
- `GET /commentaries?book=&chapter=&verse=&commentary=` lists the commentaries that have notes on the verse (with the verses each note covers) and gives the text of the one asked for, else the first, with its chapter and book introductions; 404 when none has notes. Frontend: `CommentaryPanel.tsx` (one tab per commentary, introductions in expandable sections), the "Commentaries" link in `SearchResults.tsx`. Only Bibles stored on this site get the link (the verse reference is all it needs, but the licensed Bibles have no per-verse links).
- Search inside the commentaries: a second search page, "Search the commentaries" (`SearchTab.tsx` runs one page each for the Bibles and the commentaries, each keeping its own query and results; `SearchForm.tsx` and `SearchResults.tsx` serve both through a `mode`). The form offers match all words, any word or exact phrase, one commentary or all, and the same book filters; whole words and the Bible list do not apply. `GET /search-commentaries?query=&match_mode=&commentary=&book_start=&book_end=&book=&page=&per_page=&sort_by=verse&sort_direction=` (code in `ml-service/commentaries.py`, `search_commentaries`) returns the same shape as `/search` with `source: "commentary"`, one result per note: `reference` is the verses the note covers, `commentary_id`/`commentary_name`, and `text` is an excerpt around the words found, with each found word wrapped in the control characters U+0001 and U+0002 (the page turns them into bold type). `GET /commentary-list` lists the commentaries (the tab appears only when there are some). Results are best match first (`ts_rank_cd`) unless sorted by verse (the "Verse" heading; Clear Sort goes back). Each result links to "Read the note" (the Commentaries window on that commentary, with the search words in bold) and "Show in Context" (in the BSB, else the first Bible here).
- How the matching works (migration 008): a stored `search_vector` column and a GIN index on `commentary_entries`, built with our own text search configuration `commentary_english` (English word forms, so love finds loved and loving, but **without** Postgres's list of ignored common words, so "born again" or "so loved the world" match exactly; the stock `english` configuration would drop "again", "so" and "the"). Words are not matched as parts of words (the Bible search matches inside words; this one does not), and a Bible-style "whole words" option does not apply. Adding the column recomputes every row (about 20 seconds on a laptop, longer and blocking reads of that table on the server) and adds about 180 MB with the index (the database was 361 MB before it). `import_commentaries.py` needs nothing extra: the column is generated. An excerpt is built only for the 25 or so notes on the page (it reads the whole note). Slowest case seen: a search for only common words ("the of and") about 0.5 s.
- References inside a note are links: `ml-service/scripture_references.py` finds `Book chapter:verse` (and a range `3:16-18`, linked to its first verse) in the note and in its chapter and book introductions, and `GET /commentaries` returns them as `references`, `chapter_introduction_references` and `book_introduction_references`, each `[start, end, "book:chapter:verse"]` over the text it belongs to. It accepts a book name written in capitals too (`PHI. 3:13`, `DEUT. 31:8`, as Daily Light writes them) but not a lower-case one (`job 3:4`). **A bug fixed on 2026-11-06:** after the short two-letter codes were added (`Sa`, `Ki`, `Co`...), `Isa` and `I Sa` (1 Samuel) became the same lookup key, so every `Isa 53:5` in the commentaries was linked to 1 Samuel (or dropped when 1 Samuel had no such chapter); the lookup key now keeps the space after a Roman numeral and a plain name wins a clash (`test_isaiah_is_not_taken_for_first_samuel`, `test_no_two_books_share_a_name`). It knows both spellings the six commentaries use (the short CCEL codes Psa, Kg1, Co1, Jo1, Joh, Zac, Jde, Plm and number-first forms such as 2Ki. and 1Co. in Henry, Clarke, Jamieson-Fausset-Brown and Keil and Delitzsch; the full names Psalm, 1 Kings, Song of Solomon in Gill and Calvin) and roman numerals (I John). It links only a reference that names a verse that exists, checked against the chapter lengths of the Bible with the most verses (`verse_limits`, kept for an hour); a reference to a verse that does not exist in that numbering is left plain (mostly Psalms, whose Hebrew numbering counts the title line, about 140 in all). Not linked: lists that leave the book out ("Joh 3:16, 17"), chapter-only references, the Apocrypha (Maccabees, Sirach, Tobit, Wisdom, which our Bibles do not have), and a range that runs into the next chapter beyond its first verse. On 2026-11-06 it found 270,175 references in the 77,984 notes (about 99.6% of everything shaped like a reference); the longest note, 93,000 characters, takes about 13 ms. A reference opens "Show in Context" for its first verse in the Bible of the window, on top of the note; Back returns to the same note and tab. The reference buttons are in the tab order (unlike Strong's links), and `highlightLinked` in `highlight.tsx` takes `LinkOptions` for either kind.
- Browsing without a search ("Browse the commentaries" in the sidebar, `BrowseTab.tsx`): choose a commentary, then a book, a chapter and optionally a verse and press Go (the book and chapter choosers act at once; the commentary chooser keeps the same place, and the verse when the reader is still on its chapter, so one passage can be compared across commentaries; a commentary without that book, such as Keil and Delitzsch for the New Testament, starts at its first). The page scrolls to the note that covers the verse (marked with a bar), and the reader can **scroll on past it in both directions**: chapters load above and below as the ends come near, across book boundaries, up to 9 chapters kept at once (far ones are dropped), and the book and chapter choosers follow the chapter at the top of the screen. Each note has "Show in Context" and "Other Commentaries" links, and its references are links (the same windows as in search; opening one hides the reading, and closing it puts the page back at the same scroll position and the link back in focus). The choosers stay at the top of the screen on wide windows and scroll away on phones. API: `GET /commentary-contents?commentary=` (books and the chapters with notes, for the choosers) and `GET /commentary-chapter?commentary=&book=&chapter=` (every note of the chapter in verse order with what each covers and its references, both introductions, and the `previous` and `next` chapters with notes across books; 404 when there are no notes). The largest chapter is 337,000 characters (Calvin on Psalm 119). The tab loads only when first opened. Getting back to the tabs (the top of the page): because chapters keep loading above the reader (and the reader's place is held while they do), the browser's own jump to the top never arrives, so the tab has its own: the Home key (also Ctrl+Home and Cmd+Up Arrow; not while typing in the verse box or a chooser), a bold blue floating "↑ Back to tabs" button that appears after about a screenful of scrolling, a "↑ Back to tabs" link at the right of the choosers (always in view on wide windows) and another under the last loaded chapter. Clicking any tab also scrolls to the top. (The first version labelled the floating button "↑ Top" in a small grey pill and was not noticed; keep it obvious.) Each calls `scrollToTop` from `useChapterStrip`, which also stops chapters being added above until the reader has scrolled about 800 px down again (otherwise they would carry the page away from the top).
- Shared parts of the two readers (the commentary browser and the Bible reader): `useChapterStrip.ts` is the continuous-scroll engine, independent of what is read (it needs a `load(book, chapter, signal)` returning a chapter with `previous` and `next` neighbours; it keeps the reader's place when chapters are added above, loads ahead with an IntersectionObserver and tracks the chapter on screen); `useVerseWindows.ts` holds the window stack that the search results and both readers use; `useReaderWindows.ts` adds the scroll save and restore around it; `useBackToTop.ts` and `BackToTop.tsx` are the Home key and the floating button; `NoteText.tsx` draws commentary text with reference links. The reader tabs reuse the `.browse-*` styles.
- Not built: highlighting word forms in the note itself (the note shows the words as typed in bold; the excerpt shows the forms found), and links from other places into the reader (for example a "Read the whole chapter" link in the Commentaries window). Possible next steps for references: lists that omit the book, and a choice between Show in Context and Commentaries for a clicked reference.

## Reading the Bible
- "Read the Bible" is the first entry under Bible in the sidebar (`BibleTab.tsx`; the site itself opens on the welcome page). It reads a Bible stored on this site (ASV, BSB, KJV, WEB, YLT, anything published; the licensed Bibles NIV, NASB and The Message cannot be read this way because they are never stored): choose a Bible, a book, a chapter and optionally a verse and press Go. The page goes to the verse (marked with a bar) and the reader can scroll on past it in both directions, chapter after chapter and book after book, exactly like the commentary browser (same engine, `useChapterStrip`; up to 9 chapters kept; the choosers follow the chapter at the top; the back-to-tabs controls and the Home key work the same). The BSB opens at Genesis 1 the first time. Changing the Bible keeps the place and the verse (while the reader is still on its chapter); a Bible without that book starts at its first.
- A verse has a menu with the same six things as the links of a search result: Show in Context, Full Chapter, Other Translations, Related Verses, Original Words and Commentaries (`verseMenuItems` in `BibleTab.tsx`, drawn by `VerseMenu.tsx`). Right-click a verse, or click or tap its number (the number is a button, so it also works from the keyboard and on a phone; the menu key or Shift+F10 on it opens the menu too). The menu opens at the pointer, stays inside the window, moves with the arrow keys, Home and End, chooses with Enter, and closes with Escape, a click elsewhere or any scroll. It does not replace the browser's own menu when text is selected or Shift is held, so copying still works. The first version showed the six links under every verse and was found cluttered; do not bring them back. The chosen verse is tinted while the menu is open. The windows open over the reading as before; closing one puts the page back at the same scroll position and the focus back on the verse number. (Full Chapter repeats what the page shows; it is there because it was asked for, and is one line to remove.) In the BSB the words are also clickable (Strong's numbers, as in Show in Context); the other Bibles are plain text. A hint line above the reading says how to open the menu. Verses sit on consecutive lines with no space between them (a verse is one line or a few wrapped lines; the reading is not run together as a paragraph).
- API (`ml-service/bible_reader.py`): `GET /bible-contents?translation=` (books and chapters of a Bible, for the choosers) and `GET /bible-chapter?translation=&book=&chapter=` (every verse of the chapter with `links` where the Bible has them, and the `previous` and `next` chapters across books). Licensed codes give 422; an unknown or hidden Bible, or a chapter it lacks, gives 404. The code can be written in any case.
- Not built: reading the licensed Bibles (it would cost API.Bible requests per chapter and the terms need the copyright notice and usage reporting), a choice of the Bible text next to a second Bible side by side, and word links for Bibles other than the BSB.

## Devotionals
- Four public-domain devotionals, in one reader ("Read the devotionals", the last sidebar entry; it appears only when the table has data): Spurgeon's **Morning and Evening** and **Daily Light on the Daily Path** (a morning and an evening reading for each of 366 days, February 29 included) and **The Imitation of Christ** (William Benham's 1886 translation; 4 books, 25 + 12 + 59 + 18 = 114 chapters) and **The Practice of the Presence of God** (a preface, 4 conversations, 15 letters). Code: `ml-service/devotionals.py`, `DevotionalsTab.tsx`; tables in migration 009 (`devotionals`, `devotional_sections`, `devotional_entries`). A devotional is sections (months, or books and parts) of units (days, or chapters); `kind` is `daily` or `chapters`.
- **Sources and licence.** Morning and Evening and Daily Light come from the Christian Classics Ethereal Library's ThML files (https://ccel.org/ccel/spurgeon/morneve and https://ccel.org/ccel/anonymous/daily_light; each file's header says `DC.Rights: Public Domain`; Spurgeon wrote it in 1865 and Daily Light is from the 1800s). **CCEL's own copyright policy (https://www.ccel.org/about/copyright.html) says its editions rest on books that are public domain in the United States, may have copyrighted introductions and special contents, "may be used for personal, educational, or non-profit purposes", and asks people to contact them to republish its works or use them commercially.** This site is non-commercial and uses only the text of the two books, with credit, and the files are not committed or offered for download; but it is worth asking CCEL for permission (see Open items). The Imitation (Project Gutenberg eBook #1653) and the Practice (#13871) are Gutenberg texts of 19th-century translations. **Do not use Gutenberg #5657 for the Practice: it is marked "COPYRIGHTED Project Gutenberg eBook".** CCEL's own Imitation is the 1940 Bruce translation (renewal not found, but newer); Benham's 1886 is used instead. The credit is `DevotionalCredit.tsx`, under each reading and on the "Bible copyright notices" page.
- Load by hand (the deploy script only warns when `devotional_entries` is empty); the files are git-ignored (`ml-service/data/devotionals/`, about 5 MB): `ml-service/.venv/bin/python ml-service/scripts/download_devotionals.py ml-service/data/devotionals`, then `ml-service/.venv/bin/python ml-service/scripts/import_devotionals.py ml-service/data/devotionals` (`--dry-run` first; replaces each devotional in one transaction; a file whose number of days or chapters is wrong is refused). The XML is read with `defusedxml` (in `requirements.txt`), because the files come from outside. Loaded on 2026-11-06: 732 + 732 + 114 + 20 entries.
- How they are read: the ThML books have one `div2` per reading (`Morning, January 1`), with the key verse, a line naming it, and paragraphs; Daily Light's lines of references (`John 17:24. -II Tim. 1:12. -Phi. 1:6.I Cor. 9:24,25.`) are tidied into one line per group, joined with semicolons. The Gutenberg books are read by their headings (the Imitation's contents list at the top repeats every heading, so the book is taken from the last "THE FIRST BOOK"); hard-wrapped lines are joined into paragraphs and Gutenberg's `_italic_` marks are dropped. Each text's footnotes stay at the end of its chapter.
- API: `GET /devotionals` (the list, in the order shown), `GET /devotional-contents?devotional=` (sections and their days or chapters, for the choosers) and `GET /devotional-unit?devotional=&section=&unit=` (one day or chapter: its entries, each with the scripture references found in it, and the `previous` and `next` days or chapters across months and parts). The scripture references are linked like those in commentaries (a click opens the verse in context, in the BSB). The reader is the same engine as the Bible reader and the commentary browser (`useChapterStrip`, with a section as its "book" and a day or chapter as its "chapter"): choose a devotional, a month and day (or a part and chapter), scroll on in both directions, Today (daily ones open at today's date; the day is kept when switching between the two daily books), the back-to-tabs controls and Home. 
- Not built: searching the devotionals (daily emails are built: see "Daily devotional emails"), a way to follow one chapter of the Imitation by its Latin numbering, and reading plans or bookmarks.

## Deploying
- Push to `main`, then run `deploy/deploy.sh` from your Mac (`--all` rebuilds and restarts everything). It pulls on the server, then only redoes what changed: Python dependencies and an ML service restart, the frontend build (`VITE_ML_SERVICE_URL=/api`), Composer, Drupal database updates and a cache rebuild. It then checks health, including from outside. The server deploys what is on GitHub, not your working copy.
- It unlocks Drupal's read-only settings folder only while git updates files, and locks it again afterwards (`555`, not `444`, because git tracks `settings.php` as executable).
- nginx and PHP-FPM config files need sudo, so the deploy script only reports when the installed copies differ from `deploy/`. Install them with `ssh -t bible-and-beyond sudo ~/bible-and-beyond.com/deploy/install-system-config.sh`. It replaces only changed files, tests the configuration, and puts the old files back if the test fails.
- **Caching**: nginx sends `Cache-Control: no-cache` for `index.html` (the page every address of the site is served by), so a browser checks it on each visit or reload and picks up a new release (it gets a quick "not modified" when nothing changed); before this, a tab or a browser could keep showing an old copy after a deploy and a new feature seemed to be missing. The scripts and styles in `/assets/` have a new name in every build, so they are cached for 30 days. A tab that was already open before a deploy still runs the old code until it is reloaded (it is a single-page app). `add_header` inside a `location` replaces the server's, so the two security headers are repeated there.
- Make changes in the repository and deploy them. Do not edit files on the server; that blocks `git pull`.
