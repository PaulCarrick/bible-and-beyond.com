# Bible and Beyond

A web app that answers Bible questions using AI/ML.

## Architecture
- `drupal/` — Drupal 11 (PHP), run with DDEV. Content management and admin. Exposes content via JSON:API.
- `ml-service/` — Python 3.12 + FastAPI. AI/ML logic and the question-answering API.
- `frontend/` — React + TypeScript + Vite. The public web UI; calls ml-service and Drupal.

## Local URLs
- Drupal: https://bible-and-beyond.ddev.site
- ML service: http://localhost:8000 (API docs at /docs)
- Frontend: http://localhost:5173
- Live site: https://bible-and-beyond.com (app) and https://cms.bible-and-beyond.com (Drupal); see "Production server" below

## Running locally
- Drupal: `cd drupal && ddev start` (use `ddev composer` and `ddev drush`, never local php/composer)
- ML service: `cd ml-service && source .venv/bin/activate && uvicorn main:app --reload --port 8000`
- Frontend: `cd frontend && npm run dev`
- If something else already uses port 8000 (Docker sometimes does), run uvicorn on 8001 and put `VITE_ML_SERVICE_URL=http://localhost:8001` in `frontend/.env.local` (git-ignored).

## Conventions
- No abbreviations in variable, function, or method names.
- 2-space indentation in PHP, TypeScript, JSON, YAML; follow the formatter's default for Python.
- Keep solutions simple and direct; avoid unnecessary abstractions.
- Show complete files/functions when making changes.
- Never commit secrets; use `.env` files (gitignored) and keep a `.env.example`.

## Testing
- Python: pytest — `cd ml-service && source .venv/bin/activate && python -m pytest`
- Frontend: Vitest (to be added)
- Drupal: PHPUnit via `ddev exec vendor/bin/phpunit` (to be added)

## Bible database
- Postgres 17 + pgvector in Docker (`docker compose up -d` from the repo root), container `bible-and-beyond-database`, host port 5434.
- Connection string lives in `ml-service/.env` as `DATABASE_URL` (never commit `.env`).
- Schema: `ml-service/database/schema.sql` — tables `translations`, `books` (canonical 1–66 with USFM codes and name aliases), `verses`, `verse_embeddings`. Applying it drops and recreates these tables.
- Import a translation (BSB tab format or eBible `*_vpl.txt` format): `.venv/bin/python scripts/import_bible.py data/<file>.txt --code BSB --name "Berean Standard Bible" --license "Public domain"`. KJV also needs `--strip-brackets`.
- Search in public-domain text (BSB); copyrighted translations like ESV are only fetched for display, never stored.
- Each translation has an `is_published` flag. Search and the Bible picker only see published ones. Database changes live in `ml-service/database/migrations/` as files that are safe to run twice; `deploy/deploy.sh` applies them. `schema.sql` is kept in step for fresh databases.
- The importer lives in `ml-service/bible_import/`; `scripts/import_bible.py` (command line, publishes at once unless `--unpublished`) and `scripts/manage_bibles.py` (JSON output, used by Drupal) both call it.

## Licensed Bibles (API.Bible)
- NIV, NASB 2020 and The Message come from API.Bible (free Starter plan: non-commercial only, 5,000 requests a month). Code is in `ml-service/api_bible.py`; the key and endpoint are set on the Site settings screen (see "Service keys"; first from `API_BIBLE_KEY` and `API_BIBLE_ENDPOINT` in `ml-service/.env`).
- Their text is never stored in our database; it is fetched on demand and cached in memory (search results 10 minutes, copyright metadata 24 hours; the terms require refreshing within 30 days).
- Terms to keep: show each Bible's copyright notice with its text, keep the API.Bible link and the "Bible copyright notices" page (now on the Help page and under licensed search results, no longer in the footer), and report every view to FUMS (`frontend/src/fums.ts`). Never alter the text, never use it commercially, and never put it in AI prompts or training data. Use only the public-domain local Bibles (ASV, BSB, KJV, WEB) for `/ask`.
- These Bibles are searched one at a time, matching all words, in Bible order. Match any, exact phrase, whole words, per-book counts and sorting by contents are not available for them.
- **Searching them with the Bibles on this site** (added 2026-11-08): "Search in multiple versions" lists the licensed Bibles as a second row of checkboxes. The server still takes one licensed Bible per request (it refuses a mixed list), so the page splits the choice (`splitTranslations` in `SearchTab.tsx`): the main list searches the Bibles on this site with every option, link and filter, and each licensed Bible gets a section of its own under it (`LicensedResults.tsx`: its count, its own pages, 10 verses a page when the page size is "fit the screen", its copyright notice, FUMS, no links). With only licensed Bibles chosen, the first is the main list. A section searches again only when the words, the book range or the page size change, so sorting or filtering the main list costs no API.Bible request; each page of a section is one request. The match options grey out only when every chosen Bible is licensed.
- Backend tests fake the API so they do not use the monthly allowance. Live calls count against it, so keep them few.

## Managing Bibles from Drupal
- Drupal is the admin screen for the main site; the Bible text goes into the main PostgreSQL database, never into Drupal's. Page: https://cms.bible-and-beyond.com/admin/bibles (Drupal module `drupal/web/modules/custom/bible_admin`).
- Flow: upload a `.txt` file with a code, name, language and license; see a preview (format, verse and book counts, sample verses, warnings); confirm to import. A new Bible is **hidden until published** (Publish / Hide / Delete on the list page). Re-importing an existing code replaces its text and keeps its published state. The last published Bible cannot be hidden or deleted. The codes NIV, NASB and MSG are refused (they belong to API.Bible).
- Drupal runs `ml-service/scripts/manage_bibles.py` with a fixed argument list (no shell). The uploaded file is kept in `/home/paul/drupal-private/bible-uploads/` only until the import is confirmed or cancelled, and stale ones are removed by cron after a day. Check the Drupal log (type `bible_admin`) to see who imported, published or deleted what.
- Roles: `administrator` (everything, the whole of Drupal), **`Website administrator`** (only the website's own pages: Bibles, Commentaries, Devotionals, Other books, the whole Site settings screen, Site users, FAQ notes; nothing of Drupal's own, so the sidebar shows just those seven; permissions `access administration pages`, `access navigation`, `view the administration theme`, `administer bibles`, `administer site settings`, `administer site users`, `administer faq notes`, `use text format faq_note`) and `Bible administrator` (the Bibles, Commentaries, Devotionals and Other books pages and, on the Site settings screen, only the verse-window numbers). Give the people who run the website the Website administrator role and keep `administrator` for Drupal itself. `administer site settings` is the module's own permission for the title, copyright, email and key sections of Site settings (Drupal's `administer site configuration` also allows them, for the administrator). The role comes from `config/install/user.role.website_administrator.yml` on a new install and from `bible_admin_update_11001` (in `bible_admin.install`) on a site that had the module already (`bible_admin_update_11002` adds the FAQ notes permissions, text format and editor); the containers run `drush updatedb` and `cache:rebuild` on every start of an existing site, as `deploy.sh` does. Add people at People > Add user. The server cannot send email, so set each new user's first password yourself and tell them privately.
- Adding a file format (USFM, XML, ...): write a reader class in `ml-service/bible_import/formats.py` (same members as `TabSeparatedReader`: `id`, `name`, `description`, `score`, `read`) and add it to `READERS`. Detection, the preview, the import and the Drupal format list pick it up automatically. Add tests in `ml-service/tests/test_bible_import.py`.
- The Drupal module has no automated tests yet (PHPUnit is not set up); the Python side does.

Tests: `tests/test_site_users.py` (12, real database, only their own `@site-users-test.example` accounts).

It turns on "Ask your own question" on the FAQ page (see the FAQ section); it is also in `GET /account/me` and the login answer.

Code: `drupal/web/modules/custom/bible_admin/src/Form/SiteSettingsForm.php`, `MailSettings.php`, `BibleManager::getSiteSettings()` and `saveSiteSettings()`. It replaced the "Search settings" page (`SearchSettingsForm`).

## AI search of the commentaries, devotionals, other books and music (search by meaning)
- Added 2026-11-12 at the owner's request (their example: "beatitudes", a word the Bible never uses, should find notes and readings on the Sermon on the Mount). The same rule as the Bible's AI search: the choice is in the Match list **only for a logged-in account with `open_ai_queries`**, and the server checks again (`ai_search_account` in `main.py`: 401, 403). It is on **Search the commentaries** ("Use AI to find related notes", button "Find notes with AI"), **Search everything** ("Use AI to find related passages", "Search with AI"), **Search other books** and **Search the music**. On Search everything the Bible group comes from Gemini's verse list (`find_verses`, as on the Bible page; if Gemini fails that group is left out, not the whole search) and the other groups from the embeddings.
- **How it works** (`ml-service/passage_embeddings.py`): every commentary note, devotional or book entry and song's words is cut into pieces of about 2,000 characters (whole paragraphs, a long one cut after a sentence, `cut_into_pieces`), and each piece, with a label line in front ("Matthew Henry on Matthew 5:1–12", "Morning and Evening, January, January 1, Morning"), is turned once into an **embedding** by Google's **`gemini-embedding-001`** (`RETRIEVAL_DOCUMENT`; the **first 256 of its 768 numbers**, `DIMENSIONS`, chosen by the owner on 2026-11-12 for space: the model's shorter output is exactly the start of the longer one, and the same notes came first for three test searches). They are in the table **`passage_embeddings`** (migration 026; `halfvec(256)`, a pgvector HNSW cosine index per kind; the place of each piece and its offsets in the text, and the md5 of what was sent). A search embeds only the visitor's words (`RETRIEVAL_QUERY`), reads the 300 nearest pieces of that kind, keeps the best piece per passage and lists up to 50 passages, closest first (`MOST_RESULTS`); hidden texts are left out. The excerpt is the start of the matching piece (no bold, `terms` is empty; the answers carry `ai: true`). The commentary list can still be sorted by verse and filtered by book; on Search other books the order choice is hidden in AI mode. `gemini-embedding-2` was tried and not used: it returns one embedding for a whole list of texts.
- **Making the embeddings**: `ml-service/.venv/bin/python ml-service/scripts/embed_passages.py [commentary|devotional|music] [--source=ID] [--book=N] [--dry-run] [--pieces-per-minute=N]`. A piece whose text is unchanged is skipped, so it can be stopped and run again, and **must be run again after a text is reloaded, uploaded or a song added** (else that text is not found by the AI search; nothing runs it automatically). `--dry-run` prints the pieces, the characters and an estimated price. On 2026-11-12, everything: commentaries 164,771 pieces, 181 million characters, about $6.80; devotionals and books 19,408 pieces, about $1.20; songs a few cents (at $0.15 a million tokens, the price used for the estimate; check Google's price list). It uses the Gemini key of the Site settings screen. **The key on the Mac is on Google's free tier**: 100 embedding requests a minute, each piece counting as one, and a cap on tokens a minute as well, so in practice about 20 pieces a minute (the script waits a minute and retries on each refusal; `--pieces-per-minute=90` avoids most of them). At that pace every commentary would take days; a paid key is much faster. **Space**: about 2.2 KB per piece with its index at 256 numbers (measured on 863 pieces; it was 4.5 KB at 768), so everything (184,000 pieces) should be about 400 MB. Pieces of text are sent to Google, only public-domain texts and the songs' words, never a licensed Bible.
- **Searching costs**: one embedding call per new query (kept in memory a day and in the database 30 days, `ai_cache.py`, like the Bible's AI verses; a kept one is free and not counted); each account may make 100 new ones a day (`SEARCHES_PER_DAY`, 429 after). Queries up to 300 characters; the query is never logged.
- Not in the containers' data (`make-public-data.sh` leaves the rows out; an install runs the script with its own key). The Backup and restore page includes the table (it is in the Bible database).
- Tests: `tests/test_passage_embeddings.py` (7; Google faked with a vector per topic word; their own `ai-test-` commentary and devotional and `@passage-search-test.example` accounts).

## Internet Archive search (anyone, no login)
- Added 2026-11-12 at the owner's request: **"Search the Internet Archive"** is the last choice in the Match list of every search page (the Bible and commentary search pages, Search everything, Search other books, Search the music), **for every visitor, with no account or flag**. Recordings (`audio`, the music page) use the catalogue search, leaving out mirrored podcasts. About 3 s a search; answers kept 10 minutes in memory; at most 40 pages (the Archive refuses deep pages); a failure gives 503 with a general message, and the query is not logged.
- nginx puts `/api/search-internet-archive` under the searches' limit (30 a minute per visitor; `deploy/nginx/bible-and-beyond.conf`, `docker/web/nginx.conf`); on the live server it applies only after `install-system-config.sh` (sudo). - The keys and options of the outside services are set on the Drupal **Site settings** screen (https://cms.bible-and-beyond.com/admin/site-settings), in sections that only administrators see (like the email server): **Google Gemini** (API key; models to try, comma-separated), **API.Bible** (key; address; requests a month, 0 to 5,000), **Google reCAPTCHA** (site key, which is public; secret key; minimum score, 0 to 1) and **Christian music** (the Music folder, where the song files are kept; see "Christian music"). The three keys are password fields that never show the saved value: the field says whether a key is in use and where from; leaving it empty keeps it, typing replaces it, and "Remove this key" clears it (that service then stops working on the site).
- **Where they are kept**: `ml-service/data/service_settings.json` on the server (mode 600, owned by `paul`, git-ignored), **not in either database**, so they are not in the database backups (keep a copy of the keys somewhere safe yourself; a rebuilt server starts again from its `.env`). Code: `ml-service/service_settings.py` (`get_setting(name)`, read again whenever the file changes, so a save applies at once with no restart), the Drupal tool `ml-service/scripts/manage_service_settings.py` (`get` never prints a key, only whether each is set and its source; `set` reads the values as JSON on its **standard input**, never as arguments), `BibleManager::getServiceSettings` and `saveServiceSettings`, `SiteSettingsForm::buildServiceSettings`.
- **Starting from `.env`**: until the screen is first saved, each value comes from `ml-service/.env` (`GEMINI_API_KEY`, `GEMINI_MODEL`, `API_BIBLE_KEY`, `API_BIBLE_ENDPOINT`, `API_BIBLE_MONTHLY_LIMIT`, `RECAPTCHA_SITE_KEY`, `RECAPTCHA_SECRET_KEY`, `RECAPTCHA_MINIMUM_SCORE`), else its default; the screen says "from ml-service/.env" beside such values. **The first save copies every value into the file, and from then on the screen's values are used and those `.env` lines are ignored** (they can stay as a record or be deleted). Everything else stays in `.env`: `DATABASE_URL` (needed before anything can be read), `ALLOWED_ORIGINS`, `SITE_URL`, `DRUSH_COMMAND`. The email server password stays in Drupal's configuration, as before. (`RECAPTCHA_ENABLED`, found in a local `.env`, is not read by any code.)
- Checks: the Python side refuses a bad value (model names, an `https://` address, the limits, one line each) and the screen shows the message; the Drupal log records who saved and which keys were newly typed or removed, never a key. Tests: `tests/test_service_settings.py` (13); `tests/conftest.py` points every test at a temporary settings file, so the tests never use the real one. Checked locally in DDEV (with made-up keys in a stand-in): the first save copied the `.env` keys into a mode-600 file, no key appeared in the page, a bad model list was refused, and removing a key worked.

The forms that rebuild (`SiteSettingsForm`, `SiteUserForm`, `UploadForm`, `PreviewForm`) now declare them `protected`; do the same in any new form that calls `setRebuild`.

## Contact form (main site)
- "Contact" in the sidebar (group About; `ContactPage.tsx`, also linked from the welcome page): full name, email, optional phone, and a message written in **Quill** (npm `quill`, snow theme; toolbar of bold, italic, strike, link, heading, quote, code, lists, undo and redo; no attachments), and Google **reCAPTCHA v3** (no box: the page gets a token when Send is pressed; the page names Google's policies). **The badge is drawn inside the form** (above Send Message), not in Google's usual corner spot: the script is loaded with `render=explicit` and `grecaptcha.render(container, {badge: 'inline', size: 'invisible'})`, and the token comes from `grecaptcha.execute(widgetId, {action: 'contact'})`. So the badge goes when the message is sent (the form gives way to the thank-you note) and when another page is opened, and comes back with "Send another message"; Google's floating badge never appears. The page stays mounted so a half-written message is not lost.
- Keys are set on the Site settings screen (see "Service keys"; they started in `ml-service/.env`, never committed): `RECAPTCHA_SITE_KEY` (public; the page fetches it from `GET /contact-settings`, and the form says it is unavailable when it is empty) and `RECAPTCHA_SECRET_KEY`. Create a **v3** key pair at https://www.google.com/recaptcha/admin with the domains `bible-and-beyond.com` (and `localhost` to try it locally). A v2 key gives "Invalid key type". The server accepts a score of `RECAPTCHA_MINIMUM_SCORE` or more (0.5 when not set) for the action `contact`; a refusal is logged with its score so the limit can be tuned.
- `POST /contact` (`ml-service/contact.py`): checks the fields (one line each, valid email, up to 5,000 characters of message), then the reCAPTCHA token with Google (success, action and score), then cleans the message HTML (an allowlist: paragraphs, bold, italic, strike, links with http(s) or mailto only, quotes, code, lists, headings; scripts, images and event attributes are dropped) and sends a plain-text and an HTML email. A bad message is refused before Google is asked.
- **Where the email settings come from.** They are the ones on the Drupal Site settings screen (host, port, user, password, authentication, From, To, subject). The password is only in Drupal, so for each message the ML service runs `drush php:eval` (`drupal/vendor/bin/drush`, or `DRUSH_COMMAND` in `.env`, e.g. `ddev drush` on a Mac) to read `MailSettings::load`, uses them for that one message and logs nothing from them. Mail goes out with Python's `smtplib` (STARTTLS on 587, SSL on 465, the chosen sign-in method). The visitor's address is the Reply-To; From is the site's address. A failure is logged and the visitor sees only a general "could not be sent" message (502).
- nginx limits `/api/contact` to 3 a minute per visitor (burst 3; `deploy/nginx/`; install with `install-system-config.sh`). The tests fake Google, drush and the mail server (`tests/test_contact.py`); a real send was checked locally against a stand-in mail server.
- To go live: put the two keys in the server's `ml-service/.env`, type the email password on the Site settings screen, install the nginx change, then deploy. The subject still says "Contact request from Paul-Carrick.com." until changed there.

## Accounts (main site visitors, not Drupal)
- Optional: nothing requires logging in; accounts are for user-specific features to come. The header has "Set up account" and "Log in" links (and, when logged in, the address and "Log out"; `SiteHeader.tsx`, `AccountPage.tsx`, pages `register` and `login` in `views.ts`). Set up account asks for a first and last name (required), an email, a phone number (optional) and the password twice (at least 8 characters, at most 128, no other rules; lowered from 10 on 2026-11-09 because the owner dislikes sites that are fussy about passwords) and logs the visitor in; Log in asks for email and password. `App.tsx` asks `GET /account/me` on load.
- Backend `ml-service/accounts.py`, endpoints `POST /account/register`, `/account/login`, `/account/logout`, `GET /account/me` in `main.py`. Tables `users` and `user_sessions` (migration 010). **Name and phone** (migration 020): `users.first_name`, `last_name` and `phone`, `TEXT` and nullable, because accounts set up before 2026-11-09 have none (empty is stored as NULL). `check_profile` in `accounts.py` trims them and refuses line breaks, tabs and control characters; names up to 100 characters (`NAME_LIMIT`), phone up to 40 (`PHONE_LIMIT`). **All three are optional** (the owner chose on 2026-11-09 that only the email and the password twice are required); the form labels them "(optional)". `POST /account/register` takes `first_name`, `last_name`, `phone`; the register and login answers and `GET /account/me` return all three (`''` when there is none). The form (`AccountPage.tsx`) uses `autocomplete` `given-name`, `family-name` and `tel`. They are never logged. Nothing on the site uses them yet. **They are not in `schema.sql` on purpose**: applying `schema.sql` drops and recreates the Bible tables, and it must never wipe accounts. They are in the Bible database, so backups include them (and a restore of an older backup loses newer accounts).
- Passwords: salted **scrypt** (N=2^15, r=8, p=1; Python's `hashlib`, no extra package), stored as `scrypt$N$r$p$salt$hash`, never logged or returned. A wrong password and an unknown address give the same 401 message and take about the same time. Email addresses are stored in lower case and are unique.
- Sessions: a random token in the cookie `session` (HttpOnly, SameSite=Lax, Secure over HTTPS, 30 days); the database keeps only its SHA-256, so a copy of it cannot log anyone in. Logging out deletes the session; expired ones are removed at each login. CORS allows credentials for `ALLOWED_ORIGINS` (explicit origins only; the page uses `credentials: 'include'` for the account calls).
- nginx limits `/api/account/register`, `login`, `verify`, `resend-verification`, `forgot-password` and `reset-password` to 10 a minute per visitor (burst 5). Install with `install-system-config.sh`.
- **Email verification and password reset** (migration 011: `users.email_verified_at`, table `account_tokens`). Setting up an account emails a link (`/?verify=TOKEN`, good for 72 hours, once); the account works before it is followed (the page shows a reminder with "Send it again"), and features that need a confirmed address can check `email_verified` from `GET /account/me`. "Forgot your password?" on the Log in page asks for an address; `POST /account/forgot-password` always gives the same answer and sends after answering (as a background task), so neither the words nor the time reveal whether an address has an account. The reset link (`/?reset=TOKEN`, 60 minutes, once) lets the visitor choose a new password; that logs every session of the account out and counts as confirming the address. A bad new password does not use the link up. Links are random, stored only as SHA-256, replace any earlier link of the same kind, and a new one is not sent to the same account within 60 seconds. The page takes the token out of the address bar at once, and calls the server once per link (`VerifyEmailPage.tsx`; React runs effects twice in development, which used up a link the first time it was tried).
- The emails go out through the same path as the contact form (`send_plain_message` in `contact.py`: Drupal's email settings via drush, then smtplib), from the site's "Email From:" address, so **the email password must be set on the Site settings screen**. `SITE_URL` in `ml-service/.env` is the address put in the links (`https://bible-and-beyond.com` when not set; use `http://localhost:5173` locally). A failure to send is logged without the link and never stops sign-up; the visitor can ask again. Locally, test with a stand-in mail server and `DRUSH_COMMAND` pointing at a script that prints the settings JSON.
- Administrators can add, change and delete accounts from Drupal (see "Site users").
- Not built (on purpose, for later): changing the password or the address while logged in, a visitor deleting their own account, a list of common passwords to refuse, and any feature that uses the account. Tests: `tests/test_accounts.py` (33; they collect the emails instead of sending).

## Notes (logged-in visitors)
- A user has many notes (`notes` table, migration 012, `ON DELETE CASCADE` from `users`; like `users` it is not in `schema.sql`, so re-applying that file cannot wipe it). A note has `created_at` and `updated_at`, an `item_type` (`bible_verse`, `commentary` or `devotional`), where it is, and a `body` of cleaned HTML from the editor. Where it is: `source_code` (the translation read, or the commentary id, or the devotional id) and, for a verse or a commentary note, `book_number`, `chapter`, `verse` (numbered like the KJV, as everywhere here); for a devotional, `section` and `unit` as the devotional reader numbers them. Only the owner can change or delete a note (anyone else gets 404). Each note in an answer has a `title` saying what it is about ("John 3:16", "Genesis 1:1–2 (Matthew Henry)", "November 4 (Morning and Evening)"; built in `_describe`). A note on a verse must name a verse that exists in some Bible here. One account can keep 5,000 notes (`MAX_NOTES_PER_USER`). `GET /notes` returns `{notes, total, page, per_page}`: `page` (from 1) and `per_page` (1 to 200, default 200, which is what the notes windows use), `item_type` alone to keep one kind, the place as well for one item, and `query` to keep the notes whose text has every word (up to 10), in any case and any part of a word (`ILIKE` on `body_text`, with `%` and `_` taken literally). Migration 013 added `body_text`, the note's plain text (tags are not searched, and it is set from the cleaned note on every save; the migration fills it for older notes). The title ("John 3:16", the commentary or devotional name) is not searched, only what the visitor wrote. The list calls: (the visitor's own notes, newest first, up to 200; with `item_type` and the place only the notes about that item). A verse is the same item in every Bible, so a note written in the KJV shows when the BSB is read; a commentary note also matches its commentary. The body is cleaned with the same allowlist as the contact form (`check_rich_text` in `contact.py`): at most 10,000 characters of text. Tests: `tests/test_notes.py`.
- The **"Notes" link** opens a window (`ContextKind` `note`, `NotesPanel.tsx`) with the editor (`RichTextEditor.tsx`, the Quill editor shared with the contact form) and Save, and below it the visitor's earlier notes on that item with the date and time. A window says what it is about with `VerseTarget.subject` (`NoteSubject` in `types.ts`); without one it is a verse. The links:

This broke saving a note from a search result for a while (the notes window used a form; found on 2026-11-07 and fixed). `NotesPanel.tsx` and `NoteCard.tsx` use a plain container and a `type="button"` Save.
  - **Commentary note**: "Notes" on each note in Browse the commentaries (`BrowseTab.tsx`), on each commentary search result, and under "notes on ..." in the Commentaries window (`CommentaryPanel.tsx`, opens on top of the window, Back returns). Notes on different commentaries of the same verse are separate.

The window's `VerseTarget` carries zeros for the verse (a reading has none).

The page runs from the filter and search, through the count and the list and its paging, to the add form at the bottom; the "Add a note" button beside the filter opens the form and scrolls to it (a book, chapter and verse and the editor; notes on a commentary note or a devotional reading are added from the Notes link beside them, because choosing those from a form would need pickers). The notes windows have no search, so no highlighting there.

## Daily devotional emails
- A logged-in visitor with a **confirmed email address** can have a devotional emailed every day. On the devotionals page, under the choosers, "Email me this devotional each day" (`DevotionalEmailPanel.tsx`, a `<details>`): a time of day and a time zone (the browser's by default; `Intl.supportedValuesOf`), and for a devotional with chapters the chapter to start with (the one on screen by default). Once subscribed it says when, and offers "Change the time" and "Stop the emails". It applies to that devotional only; one subscription per devotional per user.
- What is sent: a **daily** devotional (Morning and Evening, Daily Light) sends the reading for the visitor's **own local date** (the morning and evening readings together; February 29 works); one with **chapters** (the Imitation, the Practice) sends one chapter a day in order from the starting chapter and stops, with a closing line, after the last. Plain text, from the "Email From:" address on the Site settings screen, sent with Drupal's email settings through the same path as the contact form (`load_mail_settings`, once per run). Subscribing after the day's time has gone by starts tomorrow (nothing is sent at once).
- Tables: `devotional_subscriptions` (migration 014): `send_time` and `timezone` (IANA name), `next_section`/`next_unit` for chapter devotionals, `last_sent_on` (the visitor's local date), a failure counter, and `unsubscribe_token`. There is **no foreign key to `devotionals`**, so reloading a devotional never removes subscribers; deleting a user removes theirs. Not in `schema.sql`, like the other account tables.
- **The sender** is `ml-service/subscriptions.py` `send_due`, run by `scripts/send_devotional_emails.py`, which a **systemd user timer** starts every 5 minutes (`deploy/systemd/bible-and-beyond-devotional-emails.{service,timer}`; `deploy.sh` installs both and runs `systemctl --user enable --now` on the timer when `deploy/systemd/` changes; `Persistent=true`; the user lingers, so it runs without a login). So an email arrives within about five minutes after the chosen time. It is the only scheduled job on the server (backups stay manual). Check it with `systemctl --user list-timers` and `journalctl --user -u bible-and-beyond-devotional-emails`.
- Safety of the sender: only one run sends at a time (Postgres advisory lock 7281001); a subscription claims today's date **before** sending, so nothing can be sent twice; a failed send is put back and tried at the next run, up to 3 times a day, and a chapter devotional does not move on after a failure; at most 50 emails per run (`EMAILS_PER_RUN`, the rest wait for the next run) with a one-second pause (the mail server has its own limits: the paul-carrick.com one is whatever the host allows, so watch it if many people subscribe); addresses that are not confirmed are never sent to.
- **Unsubscribing**: every email ends with a link (`/?unsubscribe=TOKEN`, `UnsubscribePage.tsx`) and carries the one-click headers `List-Unsubscribe` and `List-Unsubscribe-Post` (RFC 8058) pointing at `POST /api/subscriptions/unsubscribe?token=`; no login needed, and the token can do nothing but stop that one subscription. `SITE_URL` (in `.env`) is the address put in the links.
- API (login needed except the last): `GET /devotional-subscriptions`, `PUT /devotional-subscriptions/{devotional_id}` (`send_time` "HH:MM", `timezone`, optional `start_section`/`start_unit`; 403 until the address is confirmed), `DELETE /devotional-subscriptions/{devotional_id}`, `POST /subscriptions/unsubscribe?token=`. nginx limits the unsubscribe endpoint (10 a minute, same zone as login). Tests: `tests/test_subscriptions.py` (20; they fake the mail server and pass the time in). A real run was checked locally with a stand-in mail server: nothing at the first run, one email on a new day, nothing again.
- Not built: a page listing all of a visitor's email subscriptions (each is managed on its devotional's page, or from the email), other delivery methods (the table is per devotional, not per method), HTML emails, the "Read online" deep link into a day, Bible verse or commentary emails, and a daily cap on how many people can subscribe.

## Show in Context
- **Layout of the links** (`App.css`: `.result`, `.verse-column`, `.verse-links`, `.context-link`): the links of a result (seven now) are on a line of their own under the reference and the verse text, across the whole result and flush left, in 12.5 px type with thin lines between them, so they fit on one line at normal widths and wrap neatly on a phone. `.verse-column` is `display: contents`, so the result row itself places the text beside the reference and the links on a full line below. The line before the first link of a row is hidden by pulling the row left and clipping it (each link also has `margin-left: -1px`); keep that if the links are restyled.
- Each verse in a result from a Bible stored on this site has four links, "Show in Context", "Full Chapter", "Other Translations" and "Related Verses". Each replaces the result list with a window and an X (or Escape) that goes back to the same results. The first two highlight the chosen verse (search words in bold only there). Show in Context shows some verses before and after it in reading order, with chapter headings when it crosses a chapter. Full Chapter shows the whole chapter that contains the verse and ignores the numbers below. Other Translations lists the same verse in every published Bible stored on this site (the one searched comes first, marked "This result"); a Bible that lacks that verse is left out. Results from the licensed Bibles (NIV, NASB, The Message) have no link: it would cost API.Bible requests and the text would have to be split into verses.
- The window stops at the start and end of the book. How many verses come before and after is set in Drupal at https://cms.bible-and-beyond.com/admin/site-settings (the Site settings screen) (defaults 5 before and 10 after, each 0 to 50), together with how many related verses to list (default 10, 1 to 50). They live in the `site_settings` table (migration 002), so changes apply to the public site at once. Same permission as the Bibles page.
- Code: `GET /context`, `GET /chapter`, `GET /parallel` and `GET /related` in `ml-service/main.py` and `ml-service/context.py`; settings in `ml-service/site_settings.py` and `scripts/manage_settings.py` (JSON, used by Drupal); frontend `ContextWindow.tsx` and `SearchResults.tsx`.

## Related Verses (cross references)
- Data: OpenBible.info's cross references (https://www.openbible.info/labs/cross-references/), **licensed CC BY 4.0**, based mainly on the Treasury of Scripture Knowledge (public domain). The license requires credit, which the Related Verses window and the "Bible copyright notices" page give (`frontend/src/CrossReferenceCredit.tsx`). It says the data was reformatted and that links with no positive votes were left out; keep that true if the import changes.
- It lives in the `cross_references` table (migration 003; about 341,000 rows, 42 MB), numbered like the KJV and not tied to one translation. A reference points at a verse or a range. Votes are OpenBible.info users' ranking of how useful a link is; rows with zero or negative votes are not loaded.
- Load or refresh it by hand (the deploy script only warns when the table is empty): download `cross-references.zip` from the page above, unzip it, then run `ml-service/.venv/bin/python ml-service/scripts/import_cross_references.py cross_references.txt` (`--dry-run` first). - `GET /related?translation=&book=&chapter=&verse=` lists the best-voted references first, with their text in the Bible searched, a range expanded to at most 15 verses, and a reference to a verse that Bible lacks shown without text. Only Bibles stored on this site get the link; the licensed Bibles do not.
- The window has two tabs: "Points to" (where the verse points) and "Pointed to by" (`direction=to`: the verses that have a reference beginning at it, or a range inside its chapter that contains it; a range that starts in an earlier chapter and runs through it is not matched). The data is one-way, only 25% of pairs also appear in reverse, so "Pointed to by" is a real second list (John 3:16 points to 23 verses and is pointed to by 104). Migration 004 adds the index for it.
- Each related verse has its own "Show in Context" and "Related Verses" links. They open another window on top, so you can follow a chain of references; Back goes up one level and the X or Escape closes them all and returns to the results (`WindowView` stack in `SearchResults.tsx`, `RelatedPanel.tsx`).

## Original Words (Hebrew and Greek, Strong's lexicon)
- Data: STEPBible-Data (https://github.com/STEPBible/STEPBible-Data) from STEP Bible and Tyndale House, Cambridge, **licensed CC BY 4.0**. Its README and file headers allow including the data in software without asking permission and require credit to "STEP Bible" with a link; they ask people not to post copies of the data files elsewhere. So: the files are never committed (the repository is public; `ml-service/data/stepbible/` is git-ignored), the site offers no download of them, and the API only returns the entries for one verse or one word at a time. Credit is in `frontend/src/StepBibleCredit.tsx`, shown in the Original Words and lexicon windows and on the "Bible copyright notices" page. It says the data was reformatted and that only the Greek words of the modern critical text (NA27/28) are loaded; keep that true if the import changes.
- Tables (migration 005): `original_words` (about 441,000 rows: book, chapter, verse, position, original text, transliteration, English, Strong's number, grammar) and `lexicon_entries` (about 22,700 rows). Verses are numbered like the KJV (TAHOT gives that first, with the Hebrew numbering in brackets), not tied to one translation.
- Load or refresh it by hand (the deploy script only warns when `original_words` is empty): download these into one folder, for example `ml-service/data/stepbible/`: the four TAHOT files and the two TAGNT files from "Translators Amalgamated OT+NT", and TBESH and TBESG from "Lexicons" (names may be shortened but must start with tahot, tagnt, tbesh or tbesg). Then run `ml-service/.venv/bin/python ml-service/scripts/import_original_words.py <folder>` (`--dry-run` first). It replaces every row in one transaction. Loaded on 2026-11-06 from the files on GitHub that day (441,490 words, 22,717 lexicon entries).
- Hebrew words come from the Leningrad reading only (type `L`); a joined word such as `H9003/{H7225G}` keeps the number in braces. Greek words are those whose type starts with N (NA27/28); words found only in the Textus Receptus (such as John 7:53 to 8:11) have none. A few tags carry a sense letter the lexicon lacks (H0430J, G2453); they fall back to the "G" entry of the same number (`resolve_strong_code`).
- `GET /original-words?book=&chapter=&verse=` (the words of a verse, each with its lexicon gloss, 404 when none) and `GET /lexicon?translation=&strong_code=` (an entry, the number of verses that use the word, and the first 30 in Bible order with their text in the Bible searched; licensed Bibles get 422). Code: `ml-service/original_words.py`; frontend `WordsPanel.tsx`, `LexiconPanel.tsx`, and the "Original Words" link in `SearchResults.tsx`. Each lexicon verse has "Show in Context" and "Original Words" links, so the windows chain like Related Verses. Only Bibles stored on this site get the link.
- Search by Strong's number: a search box query that is only a number (`G25`, `g0025`, `H7225`, `H7225G`; letters and spaces forgiven, parsed by `parse_strong_query` in `ml-service/search.py`) lists the verses that contain that Hebrew or Greek word, in the Bibles chosen, with the usual book filter, sorting and paging (the match options do not apply and nothing is bolded). A number without a sense letter also matches its senses (H7225 covers H7225G and the others); a letter narrows it (H7225G only). The response adds `strong` (the lexicon entry chosen: the number itself, else its "G" sense, else the first) and the page shows a note under the heading with an "Open the lexicon entry" link (`openLexicon` in `SearchResults.tsx`; it opens the same lexicon window as a Strong's number in Original Words, with the first Bible searched for the verse text). A number that is not in the lexicon gives a 422 message; the licensed Bibles refuse it (422). A real English search that happens to look like a number (for example "H1") is treated as a Strong's search.
- Click an English word (Berean Standard Bible only): in the Show in Context and Full Chapter windows, the words of a BSB verse are buttons that open the lexicon entry of the Hebrew or Greek word behind them (a hint line says so; Back returns to the passage). Data: the Berean Bible's translation tables, `bsb_tables.tsv` (https://bereanbible.com/bsb_tables.tsv, about 85 MB), **public domain** (the Berean texts were placed in the public domain on 2023-04-30), so no credit is required. The file is git-ignored (`ml-service/data/bsb_tables.tsv`). It lists every original word with its Strong's number and the BSB English for it, in English order. We do not rebuild verses from it (spacing and punctuation differ); `ml-service/word_links.py` walks its English words in order and matches them to the words of our stored text, and a verse gets links only if every table word is found in order (on 2026-11-06: 31,082 of 31,086 verses, 719,917 linked words). Links are stored in `verse_word_links` (migration 006) as `[start, end, "H7225"]` over the verse text, with the md5 of the text they were made for; the lookup ignores them if the verse text has changed, so **run the loader again after re-importing the BSB**: `ml-service/.venv/bin/python ml-service/scripts/import_word_links.py ml-service/data/bsb_tables.tsv` (`--dry-run` first; the deploy script warns when the table is empty). The numbers are plain Strong's numbers ("H7225"); `/lexicon` accepts them and gives the main entry with the verses of every sense. Common words such as "the" and "and" are linked too, to what the table says they translate. The buttons are out of the tab order (hundreds per chapter); keyboard users use the Original Words window, which lists the same numbers. Not done: other Bibles (a public-domain Bible with Strong's numbers, such as the KJV, would need its own data), and the result rows themselves (only the two reading windows have clickable words).

## Managing commentaries and devotionals from Drupal
- Two admin pages, **Commentaries** (https://cms.bible-and-beyond.com/admin/commentaries) and **Devotionals** (`/admin/devotionals`), in the admin menu beside Bibles, for whoever has `administer bibles` (Website and Bible administrators). One controller and set of forms serves both through `{collection}`: `LibraryListController`, `ChangeLibraryForm` (confirm Publish, Hide, Delete, Refresh), `LibraryUploadForm` and `LibraryPreviewForm` (upload, preview, import, like the Bibles'); `BibleManager::listLibrary`, `changeLibrary`, `previewLibrary`, `importLibrary`. Drupal runs `ml-service/scripts/manage_library.py` (`list`, `publish`, `unpublish`, `delete`, `refresh`, `preview`, `import`; JSON answers), which uses `library_admin.py` and `library_upload.py`.
- **Publish / Hide** (migration 016: `is_published` on `commentaries` and `devotionals`, default true): a hidden commentary is left out of `/commentary-list`, `/commentaries`, `/commentary-contents`, `/commentary-chapter` and `/search-commentaries`; a hidden devotional out of `/devotionals`, `/devotional-contents` and `/devotional-unit`, its daily emails pause (the sender joins on `d.is_published`) and new subscriptions are refused (404), while a visitor's existing subscription to it is still listed so it can be stopped. Nothing stops every commentary or devotional being hidden (their sidebar entries then go).
- **Delete** removes the text; visitors' notes on it stay (their titles fall back to the id), and a devotional's email subscriptions are deleted with it. A known one can be loaded again with Load.
- **Refresh** (the six in `COMMENTARIES`, the four in `DEVOTIONALS`, also **Load** for one of them that is not in the database): downloads it again from its source and replaces its text, keeping its published state. It takes minutes, longer than a page may wait, so `library_admin.refresh` starts `manage_library.py run-refresh` as a separate process and returns; the progress is in `ml-service/data/refresh/<kind>-<id>.json` (git-ignored, with a `.log`), shown on the page, which reloads itself every 15 seconds while one runs. A refresh silent for two hours is shown as failed.
- **Upload** (`library_upload.py`; the format is described on the upload form): **a short text of one chapter (devotional by chapter or Other book) can be plain text** (added 2026-11-10: no tabs anywhere; the first line is the title of the part and the chapter, each further line a paragraph, blank lines dropped; a daily devotional cannot); otherwise tab-separated UTF-8 with a header row; in the text `\n` is a new line. A commentary: `book chapter verse end_verse text` (book as 1 to 66, a code or a name; end_verse empty, a later verse, or `end`; verse empty for a chapter introduction, chapter 0 for the book's). A devotional: `section section_title unit unit_title heading text` (daily: month and day, titles filled in; by chapter: titles needed on the first row of each; several rows of one unit are its parts). Problems are reported by line and stop the import; warnings (a verse not in the Bibles here, days with no reading) do not. The ids of the known ones are refused (use Refresh). A new upload is hidden until published; uploading the same id again replaces the text and keeps the state. An uploaded commentary records its own `source_name`, `source_url` and `license_url` (migration 016; the known ones say Free Use Bible API), and `CommentaryCredit.tsx` and the Copyright page credit it by those.
- `commentaries.save_commentary` and `devotionals.save_devotional` save either kind (the import scripts use them through `replace_commentary` and `replace_devotional`). Tests: `tests/test_library.py` (9). `scripts/apply_migrations.py` applies every migration (the containers run it on every start).

The containers do not ship Wesley's Notes: `docker/make-public-data.sh` takes its rows out of the dump (`owner_commentaries`, checked) and `fetch-owner-data.sh` fetches it from CCEL at start, hidden. Tests: `tests/test_commentaries.py`.
- A seventh commentary, **Martin Luther's Commentary on Galatians** (1535, Theodore Graebner's 1939 translation; Project Gutenberg #1549, not marked copyrighted there), is a plain-text eBook: `GUTENBERG_COMMENTARIES` in `ml-service/commentaries.py` (id `luther-galatians`, book 48), read by `read_gutenberg_commentary`. A "VERSE 6." or "VERSES 11, 12." heading starts a note, headings that repeat the verse in a row are joined into one note (Luther takes a verse a phrase at a time), each note runs to the next (like Henry's), the preface is the book introduction and the text between a chapter heading and its first verse the chapter introduction (only chapter 5 has one). 141 notes cover every verse of the six chapters. `KNOWN_COMMENTARIES` (the six and this one) is what the scripts, Load/Refresh and the upload check use; `download_commentaries.py` and `import_commentaries.py` take `luther-galatians` like the others. - Tables (migrations 007 and 008): `commentaries` (id, names, order), `commentary_entries` (book, chapter, verse, end_verse, text; about 78,000 rows, 134 MB) and `commentary_introductions` (book introductions are chapter 0). Verses are numbered like the KJV. An entry covers `verse` to `end_verse`; NULL means to the end of its chapter. Gill, Clarke and Jamieson-Fausset-Brown comment verse by verse and skip some verses; Henry, Calvin and Keil and Delitzsch comment on sections, so an entry runs from its verse to the next entry (`COMMENTARIES` in `ml-service/commentaries.py` says which is which).
- Download and load by hand (the deploy script only warns when `commentary_entries` is empty). The files are git-ignored (`ml-service/data/commentaries/`, about 245 MB): `ml-service/.venv/bin/python ml-service/scripts/download_commentaries.py ml-service/data/commentaries` (about 6,000 files, a few minutes, four connections at a time, can be stopped and rerun; a few chapters do not exist on the host and are skipped), then `ml-service/.venv/bin/python ml-service/scripts/import_commentaries.py ml-service/data/commentaries` (`--dry-run` first; replaces each commentary in one transaction; name commentaries after the folder to load only some). Frontend: `CommentaryPanel.tsx` (one tab per commentary, introductions in expandable sections), the "Commentaries" link in `SearchResults.tsx`. Only Bibles stored on this site get the link (the verse reference is all it needs, but the licensed Bibles have no per-verse links).
- Search inside the commentaries: a second search page, "Search the commentaries" (`SearchTab.tsx` runs one page each for the Bibles and the commentaries, each keeping its own query and results; `SearchForm.tsx` and `SearchResults.tsx` serve both through a `mode`). - How the matching works (migration 008): a stored `search_vector` column and a GIN index on `commentary_entries`, built with our own text search configuration `commentary_english` (English word forms, so love finds loved and loving, but **without** Postgres's list of ignored common words, so "born again" or "so loved the world" match exactly; the stock `english` configuration would drop "again", "so" and "the"). Words are not matched as parts of words (the Bible search matches inside words; this one does not), and a Bible-style "whole words" option does not apply. Adding the column recomputes every row (about 20 seconds on a laptop, longer and blocking reads of that table on the server) and adds about 180 MB with the index (the database was 361 MB before it). `import_commentaries.py` needs nothing extra: the column is generated. An excerpt is built only for the 25 or so notes on the page (it reads the whole note). Slowest case seen: a search for only common words ("the of and") about 0.5 s.
- References inside a note are links: `ml-service/scripture_references.py` finds `Book chapter:verse` (and a range `3:16-18`, linked to its first verse) in the note and in its chapter and book introductions, and `GET /commentaries` returns them as `references`, `chapter_introduction_references` and `book_introduction_references`, each `[start, end, "book:chapter:verse"]` over the text it belongs to. It accepts a book name written in capitals too (`PHI. 3:13`, `DEUT. 31:8`, as Daily Light writes them) but not a lower-case one (`job 3:4`). **A bug fixed on 2026-11-06:** after the short two-letter codes were added (`Sa`, `Ki`, `Co`...), `Isa` and `I Sa` (1 Samuel) became the same lookup key, so every `Isa 53:5` in the commentaries was linked to 1 Samuel (or dropped when 1 Samuel had no such chapter); the lookup key now keeps the space after a Roman numeral and a plain name wins a clash (`test_isaiah_is_not_taken_for_first_samuel`, `test_no_two_books_share_a_name`). It knows both spellings the six commentaries use (the short CCEL codes Psa, Kg1, Co1, Jo1, Joh, Zac, Jde, Plm and number-first forms such as 2Ki. and 1Co. in Henry, Clarke, Jamieson-Fausset-Brown and Keil and Delitzsch; the full names Psalm, 1 Kings, Song of Solomon in Gill and Calvin) and roman numerals (I John). It links only a reference that names a verse that exists, checked against the chapter lengths of the Bible with the most verses (`verse_limits`, kept for an hour); a reference to a verse that does not exist in that numbering is left plain (mostly Psalms, whose Hebrew numbering counts the title line, about 140 in all). Not linked: lists that leave the book out ("Joh 3:16, 17"), chapter-only references, the Apocrypha (Maccabees, Sirach, Tobit, Wisdom, which our Bibles do not have), and a range that runs into the next chapter beyond its first verse. On 2026-11-06 it found 270,175 references in the 77,984 notes (about 99.6% of everything shaped like a reference); the longest note, 93,000 characters, takes about 13 ms. A reference opens "Show in Context" for its first verse in the Bible of the window, on top of the note; Back returns to the same note and tab. The reference buttons are in the tab order (unlike Strong's links), and `highlightLinked` in `highlight.tsx` takes `LinkOptions` for either kind.
- Browsing without a search ("Read the commentaries" in the sidebar and on the welcome card, `BrowseTab.tsx`; it was "Browse commentaries"): choose a commentary, then a book, a chapter and optionally a verse and press Go (the book and chapter choosers act at once; the commentary chooser keeps the same place, and the verse when the reader is still on its chapter, so one passage can be compared across commentaries; a commentary without that book, such as Keil and Delitzsch for the New Testament, starts at its first). The page scrolls to the note that covers the verse (marked with a bar), and the reader can **scroll on past it in both directions**: chapters load above and below as the ends come near, across book boundaries, up to 9 chapters kept at once (far ones are dropped), and the book and chapter choosers follow the chapter at the top of the screen. Each note has "Show in Context" and "Other Commentaries" links, and its references are links (the same windows as in search; opening one hides the reading, and closing it puts the page back at the same scroll position and the link back in focus). The choosers stay at the top of the screen on wide windows and scroll away on phones. API: `GET /commentary-contents?commentary=` (books and the chapters with notes, for the choosers) and `GET /commentary-chapter?commentary=&book=&chapter=` (every note of the chapter in verse order with what each covers and its references, both introductions, and the `previous` and `next` chapters with notes across books; 404 when there are no notes). The largest chapter is 337,000 characters (Calvin on Psalm 119). The tab loads only when first opened. Getting back to the tabs (the top of the page): because chapters keep loading above the reader (and the reader's place is held while they do), the browser's own jump to the top never arrives, so the tab has its own: the Home key (also Ctrl+Home and Cmd+Up Arrow; not while typing in the verse box or a chooser), a bold blue floating "↑ Back to tabs" button that appears after about a screenful of scrolling, a "↑ Back to tabs" link at the right of the choosers (always in view on wide windows) and another under the last loaded chapter. Clicking any tab also scrolls to the top. (The first version labelled the floating button "↑ Top" in a small grey pill and was not noticed; keep it obvious.) Each calls `scrollToTop` from `useChapterStrip`, which also stops chapters being added above until the reader has scrolled about 800 px down again (otherwise they would carry the page away from the top).
- Shared parts of the two readers (the commentary browser and the Bible reader): `useChapterStrip.ts` is the continuous-scroll engine, independent of what is read (it needs a `load(book, chapter, signal)` returning a chapter with `previous` and `next` neighbours; it keeps the reader's place when chapters are added above, loads ahead with an IntersectionObserver and tracks the chapter on screen); `useVerseWindows.ts` holds the window stack that the search results and both readers use; `useReaderWindows.ts` adds the scroll save and restore around it; `useBackToTop.ts` and `BackToTop.tsx` are the Home key and the floating button; `NoteText.tsx` draws commentary text with reference links. The reader tabs reuse the `.browse-*` styles.
- Not built: highlighting word forms in the note itself (the note shows the words as typed in bold; the excerpt shows the forms found), and links from other places into the reader (for example a "Read the whole chapter" link in the Commentaries window). Possible next steps for references: lists that omit the book, and a choice between Show in Context and Commentaries for a clicked reference.

- Backend `ml-service/playlists.py`: tables `playlists` (`user_id` `ON DELETE CASCADE` from `users`, `name`, a unique index on `(user_id, lower(name))`) and `playlist_songs` (`playlist_id`, `position` from 1, `song_id` `REFERENCES music_tracks ON DELETE CASCADE`, so deleting a song takes it out of every playlist) in migration 025; not in `schema.sql`, like the other account tables, and `make-public-data.sh` leaves their rows out (`personal_tables`). `GET /playlists` (the visitor's, by name, each with `song_ids` in order, **published songs only**: a song hidden later stays in the playlist and comes back when published again), `POST /playlists` `{name, song_ids}` (`{playlist, replaced}`; only published songs, else 422; a repeated song is dropped; the name trimmed, 1 to 100 characters) and `DELETE /playlists/{id}`. All need the session cookie (401); another visitor's playlist is 404. Limits: 100 playlists an account (409 after; replacing one is still allowed) and 500 songs a playlist. Tests: `tests/test_playlists.py` (8, real database, their own `playlists-test-*` songs and `@playlists-test.example` accounts). Checked locally on 2026-11-12 with a temporary account (deleted afterwards) and the two hymns published for the check (hidden again): the checkboxes in one column, save, Change, Play with the second song starting by itself when the first ended, the end message, a phone width, and nothing shown when logged out.

## Containers (open-source install on any server)
- `docker/` lets anyone run the whole site on their own server: `docker/compose.yml` (project `bible-and-beyond-stack`, separate from the development database in the root `docker-compose.yml`, which is project `bible-and-beyond`; keep the names different) with two containers. **web** (`docker/web/Dockerfile`, Debian 13, PHP 8.4, Python 3.13): nginx with the public site on port 80 (`/api/` to the Python service) and the Drupal admin on port 8081, run by supervisord with PHP-FPM, uvicorn and a loop that runs `send_devotional_emails.py` every 5 minutes, all as the user `site`; the same rate limits as production, and the visitor's address taken from X-Forwarded-For only from private networks (a proxy that handles HTTPS goes in front). **database** (`docker/database/Dockerfile`, `pgvector/pgvector:pg17-trixie` plus MariaDB 11.8), only on the compose network `database`, which is `internal: true` and shared only with web: no port, nothing else reaches it, no route to the internet (web is also on `public`, for its ports and the outside services). Ports `SITE_PORT` (80) and `ADMIN_PORT` (8081) on all addresses. Installers read `docker/README.md`; every setting is in `docker/.env` (template `docker/.env.example`, git-ignored copy).
- **The data**: `docker/make-public-data.sh` dumps the live Bible database on the server with `--exclude-table-data` for the visitor tables (`users`, `user_sessions`, `account_tokens`, `notes`, `devotional_subscriptions`, `playlists`, `playlist_songs`, `conversation_posts`) and for the tables whose owners ask not to be redistributed (`original_words`, `lexicon_entries`: STEPBible; `devotionals`, `devotional_sections`, `devotional_entries`: two are CCEL's): their structure, no rows (it checks). The result, `docker/public-data/bible-data.sql.gz` (74 MB, git-ignored), holds the Bibles, commentaries, cross references and BSB word links; the database image has it built in and loads it on the first start (`load-bible-data.sh`). **Each site fetches the rest from the owners**: `docker/web/setup/fetch-owner-data.sh` runs once at every web start (supervisord) and, when `original_words` or `devotional_entries` is empty, runs `scripts/download_stepbible.py` (the 8 TAHOT/TAGNT/TBESH/TBESG files from STEPBible's GitHub, listed through its API) and `import_original_words.py`, or `download_devotionals.py` and `import_devotionals.py`, then deletes the files; a failure is retried at the next start. The owner's view, and the reason for this split: shipping data to whoever installs it cannot be fenced (they control the machine), so what the owners ask not to be passed on is fetched from them instead. **No source data file** is in the repository or the images: `.dockerignore` keeps them, every `.env`, `settings.local.php` and the service settings out. Drupal's production database is never used.
- **The first start** (`docker/web/entrypoint.sh`, when Drupal is not installed): `drush site:install standard`, then the administrator's password from `ADMIN_PASSWORD` (set by `setup/set-admin-password.php` from the environment, never on a command line; when empty a random one is printed once in the log), `pm:install bible_admin`, the email server from `SMTP_*` (`setup/save-mail-settings.php`), and the site title and copyright line from `SITE_TITLE` and `SITE_COPYRIGHT`. The service keys come from `docker/.env` until the Site settings screen is saved. `MailSettings::DEFAULTS` no longer holds the owner's addresses (the live site has its own values saved). Drupal's hash salt is made on the first start and kept in a volume; `DRUPAL_TRUSTED_HOSTS` adds the admin's host names.
- **Publishing**: `docker/publish.sh` builds both images for amd64 and arm64 and pushes them to `IMAGE_REGISTRY` (`ghcr.io/paulcarrick`), then copies them to `IMAGE_MIRRORS` (Docker Hub, `docker.io/paulcarrick`, by default; `docker buildx imagetools create`, three tries, as a large layer sometimes drops: the first copy on 2026-11-07 took 10 minutes for the web image and the database image needed a second try); installers can set `IMAGE_REGISTRY=docker.io/paulcarrick`; the compose file names those images, so an installer can `pull` instead of building. Pushing makes them public: only when the owner says so. **Last published 2026-11-10, a second time that evening** (at the owner's request, `latest`, amd64 and arm64, the same digests on both registries: database `sha256:594a74c4…`, web `sha256:90864deb…`; the first copy of the database image to Docker Hub dropped and the script's retry finished it), with the data refreshed that day by `make-public-data.sh` (it now leaves out the `music_tracks` rows and keeps the `faq_notes`, 15 then); copying the database image to Docker Hub took about 9 minutes.
- `OUTGOING_EMAIL=off` (in `contact.py`'s `load_mail_settings`) stops every email, for a test copy; it is `on` by default.
- Pitfalls found while building them: Debian's nginx `fastcgi_params` passes `HTTP_HOST` without the port (Drupal then redirects to the wrong port; the container passes `$http_host`); files copied from a Mac working copy can be mode 600 (the image runs `chmod -R a+rX` on the code); `pg_isready` over the socket answers while the first start is still loading (the health check uses TCP).

## Security (checked on 2026-11-07)
- A review found no way in (parameterized SQL everywhere, an allowlist HTML cleaner for notes and messages, permission checks on every Drupal admin route, the Python tools started without a shell, only ports 22, 80 and 443 open, SSH by key only, no secrets in the repository or its history) and fixed these: Drupal core 11.4.11 to 11.4.12 (it pins Symfony, which had 13 advisories fixed in 7.4.23; run `composer audit` in `drupal/` from time to time, and `pip-audit -r requirements.txt` and `npm audit` likewise); a **10-second limit on every query of the web service** (`search.STATEMENT_TIMEOUT_MILLISECONDS`, set in `main.py` only, so imports and Drupal's tools have none; a stopped query gives a 503 asking for more specific words); the searches (`/api/search`, `/search-commentaries`, `/search-other-books`, `/search-everything`) have their own nginx limit, 30 a minute per visitor (zone `api_search`); the ML service's `/docs`, `/redoc` and `/openapi.json` are blocked by nginx on the live site and in the containers (still there locally at http://localhost:8000/docs); the main site sends HSTS (a year), `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'; object-src 'none'; base-uri 'self'` (repeated in each location that has its own `add_header`; a full script policy was not added, the contact page loads Google's reCAPTCHA); the admin site sends HSTS, hides Drupal's `X-Generator` header and does not serve `CHANGELOG.txt`, `INSTALL.txt`, `README.md` and the like (capitalised `.txt`/`.md` at the root or in `core/`; `robots.txt` is still served). The old placeholder `POST /ask` was removed.
- Known and accepted: Quill 2.0.3 has a low advisory (XSS in its HTML export); notes and messages are cleaned on the server, and a note is only shown to its owner. Not done: two-factor login for Drupal administrators (the TFA module) and fail2ban (SSH takes keys only).

## Deploying
- Push to `main`, then run `deploy/deploy.sh` from your Mac (`--all` rebuilds and restarts everything). It pulls on the server, then only redoes what changed: Python dependencies and an ML service restart, the frontend build (`VITE_ML_SERVICE_URL=/api`), Composer, Drupal database updates and a cache rebuild. It then checks health, including from outside. The server deploys what is on GitHub, not your working copy.
- It unlocks Drupal's read-only settings folder only while git updates files, and locks it again afterwards (`555`, not `444`, because git tracks `settings.php` as executable).
- nginx and PHP-FPM config files need sudo, so the deploy script only reports when the installed copies differ from `deploy/`. Install them with `ssh -t bible-and-beyond sudo ~/bible-and-beyond.com/deploy/install-system-config.sh`. It replaces only changed files, tests the configuration, and puts the old files back if the test fails.
- **Caching**: nginx sends `Cache-Control: no-cache` for `index.html` (the page every address of the site is served by), so a browser checks it on each visit or reload and picks up a new release (it gets a quick "not modified" when nothing changed); before this, a tab or a browser could keep showing an old copy after a deploy and a new feature seemed to be missing. The scripts and styles in `/assets/` have a new name in every build, so they are cached for 30 days. A tab that was already open before a deploy still runs the old code until it is reloaded (it is a single-page app). `add_header` inside a `location` replaces the server's, so the two security headers are repeated there.
- Make changes in the repository and deploy them. Do not edit files on the server; that blocks `git pull`.

## Backup and restore (Drupal admin: a zip saved on the administrator's computer)
- https://cms.bible-and-beyond.com/admin/backup-restore ("Backup and restore" in the admin menu; added 2026-11-12 at the owner's request so that a new container or server loses nothing). **The backups are never kept on the server** (the owner's choice: the server or container may go away): the page has the server build one zip, the browser saves it into a folder on the owner's computer, then the server's copy is deleted; to restore, the page uploads a zip from that folder and the server restores it.
- **Two checkboxes, Database and Files**, used for both backing up and restoring (both ticked by default; at least one). *Database*: the whole Bible database (`pg_dump` custom format: Bibles, commentaries, devotionals and books, songs' details, site users with notes and daily emails, FAQ notes and answers, site settings), Drupal's database (`drush sql:dump`, cache and watchdog tables as structure only: administrators, roles, Drupal's configuration with the email server and its password) and the service keys (`service_settings.json`, `api_bible_usage.json`). *Files*: the music folder (songs and words files) and Drupal's public files (without the generated css, js, php). Restoring a part the zip lacks is refused. The zip (`bible-and-beyond-YYYY-MM-DD-HHMMSS.zip`, media stored, text compressed, with `manifest.json`: format 2, note, parts, counts) holds personal data and the keys: keep it private.
- **Folder picking** (`js/backup.js`): Chrome and Edge save straight into a chosen folder (`showDirectoryPicker`; the restore's file picker opens in the same folder); other browsers download the zip like any file (the page then offers "Delete the copy on the server") and restore through an ordinary file chooser. A backup waiting on the server (a save that did not finish) is offered again when the page opens.
- **Restore** needs "RESTORE" typed. The zip is uploaded in 8 MB parts (`BackupController::CHUNK_BYTES`, under the live server's 16 MB limits) to `ml-service/data/backup/incoming/upload.zip`, checked (every file's CRC, a manifest of format 2, no unsafe names), then restored in the background: the Bible database **in one transaction** (everything of ours in the public schema dropped, the dump loaded through `pg_restore --file=- | psql`, so a failure changes nothing; the extensions are not dropped or created, since only a superuser may create pgvector, and the restore stops if one is missing), the migrations applied, the service settings (keeping this server's `music_folder`), the files copied over, then Drupal's database (`drush sql:drop`, `sql:cli`, `updatedb`, `cache:rebuild`). Restoring the database logs the administrator out; the page says to log in again **with an account and password from the backup**, and shows how the restore ended once back. The uploaded zip is deleted afterwards, whether it worked or not.
- Code: `ml-service/site_backup.py`, `scripts/manage_backup.py` (`status`, `backup`, `discard`, `restore`, `discard-upload`, `clear-status`, `--database`, `--files`; the jobs run as `run-backup`/`run-restore` in a separate process like a library refresh, progress in `data/backup/status.json` and `job.log`; one job at a time); Drupal `BackupController` (the page, `status`, `download/{name}`, and POST `start|discard|upload|restore|dismiss` with the `X-CSRF-Token` header), `BibleManager::backupStatus`, `startBackup`, `discardBackup`, `startRestore`, `clearBackupStatus`, `backupWorkDirectory`; `css/backup.css`. Permission **`administer backups`** (restricted): only the `administrator` role (not Website or Bible administrators, since a restore replaces Drupal's own users). The Drupal log records who started a backup or a restore (logged before it starts, because the restore replaces the log).
- Needs `pg_dump`, `pg_restore`, `psql` of PostgreSQL 17 or newer and `mariadb-dump`/`mariadb` on the machine Drupal runs on: the live server has them (native PostgreSQL 17 and MariaDB); the web image now installs `postgresql-client-17` and `mariadb-client`. `POSTGRES_BIN_DIRECTORY` can point at other PostgreSQL tools (the Mac's Homebrew `pg_dump` is 15 and cannot dump the version-17 database). The tool sets a default `PATH` and `HOME`, because PHP-FPM on the live server clears the environment. While a backup is waiting or a zip is being restored it takes its size again in `ml-service/data/backup/` (the live server's disk).
- Tests: `tests/test_site_backup.py` (8; the PostgreSQL tools and drush faked). Checked on 2026-11-12 with two fresh container stacks built from the working copy: a 108 MB backup of stack A (8 s), downloaded, uploaded to stack B in parts and restored (25 s): B then had A's site user, music file and Drupal file, and A's Drupal account logged in with A's password; a files-only backup and a refused non-backup zip were also tried through the page. Not tried by hand: the native folder dialog (automation cannot click it), and a backup of the live site.
- Found while testing: the web image used to contain whatever was in the local `ml-service/data/music` (the two hymn videos); `.dockerignore` now leaves that folder out. The service keys of a container that come from `docker/.env` (never saved on the Site settings screen) are not in `service_settings.json`, so not in the backup; save the Site settings screen once to include them.
